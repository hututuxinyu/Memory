## 一、阶段1：首次生成 + 生成准确性增强

> **解决的问题**：生成文档不准确（整体策略第2点）
>
> **目标**：从源头提升生成准确率，80%→85%

### 1.1 问题分析

specgo 的 analyze skill 生成文档时有三类不准确：

| 不准确类型 | 原因 | 例子 |
|-----------|------|------|
| 语义偏差 | LLM不懂业务术语，按字面意思写 | 把"回收"写成"关闭"、把"Muen SDK"当启动器 |
| 遗漏不完整 | LLM从代码文本推断，漏看参数/返回值/调用关系 | 接口文档漏写返回值、流程文档漏写中间步骤 |
| 数值过时 | LLM把代码里的具体数值写进文档 | 写死"检查周期1800000ms"，代码改了文档就错 |

### 1.2 增强1：领域大模型注入（来源：StructMem Ω + 来源B）

**原理**：在 analyze skill 执行时，调用领域大模型（来源B）校验生成内容的业务语义。

```
specgo biz-rules-analyze 生成rules-browser.md时:

Step 1: LLM读代码提取规则草案:
  "BrowserCloserTask在心跳过期时关闭实例"

Step 2: 调用领域大模型校验:
  输入: "delete()内先uploadUserData再remove再reportUsage"
  问: "这个业务动作的正确术语是什么?"
  领域大模型推理: "含上传+删除+上报 → 是'回收'不是'关闭'"

Step 3: LLM用校验后的正确术语:
  "BrowserCloserTask回收不活跃实例"
  ✅ 从源头消除语义偏差
```

**涉及哪些 specgo skill**：

| specgo skill | 领域大模型校验什么 | 预防什么 |
|--------------|------------------|---------|
| biz-rules-analyze | 规则描述的术语 | 规则语义偏差 |
| biz-lexicon-analyze | 术语释义的准确性 | 术语表不准 |
| arch-interaction-model-analyze | 流程步骤的术语 | 交互模型语义偏差 |
| arch-structure-model-analyze | 模块职责描述 | 结构模型语义偏差 |

### 1.3 增强2：代码AST感知（来源：StructMem）

**原理**：在 analyze skill 执行前，用 tree-sitter 解析代码AST，把结构化信息喂给LLM，而非纯文本推断。

```
specgo biz-interface-analyze 生成interface-browser.md时:

原方式: LLM读browser.py源码文本 → 推断接口签名
  风险: 可能漏看返回值、参数类型

增强后: tree-sitter解析AST:
  函数: create_browser(executable_path: str, userdata: str, extensions: list)
  返回: BrowserContext
  调用: playwright.chromium.launch(), BrowserWrapper.register()
  被调用: browser-gateway ClientImpl.java

  LLM同时看源码+AST → 接口文档不漏参数/返回值
  ✅ 从源头消除遗漏不完整
```

### 1.4 增强3：类型先验引导（来源：A-MAC）

**原理**：在 analyze skill 提示词中增加信息类型引导，半持久信息不写死数值。

```
增强后提示词:
  "半持久信息(配置值/阈值/超时时间): 标注'以配置为准'，不写死数值"

效果:
  原来会写: "检查周期1800000ms" (❌ 数值写死了)
  增强后写: "检查周期由browsergw.scheduled.check-browser-period配置，
            代码默认1800000ms，application.yaml可覆盖" (✅)
  
  → 代码改了配置值，文档仍然准确
  ✅ 从源头消除数值过时
```

### 1.5 阶段1效果

| 不准确类型 | 无增强 | 有阶段1增强 | 减少 |
|-----------|--------|-----------|------|
| 语义偏差 | ~50条 | ~10条 | 80%↓ |
| 遗漏不完整 | ~60条 | ~15条 | 75%↓ |
| 数值过时 | ~40条 | ~10条 | 75%↓ |
| **准确率** | **80%** | **85%** | **+5%** |

## 二、阶段2：存疑自动识别 + 田主确认

> **解决的问题**：全量审核成本高（整体策略第1点）
>
> **目标**：1000条声明自动识别存疑项，只把~250条给田主

### 2.1 问题分析

首次生成后（即使阶段1增强了），仍有15%的声明可能有质量问题。如果让田主全量审核1000条，成本太高（4人天）。需要自动识别哪些"存疑"，只把存疑的给田主。

### 2.2 specgo spec-asset-audit 已有基础

specgo 已有 `spec-asset-audit` 做两维度审核：

| 已有维度 | 规则 | 能发现什么 |
|---------|------|-----------|
| 表达质量 E1-E5 | 句子完整/弱表述/术语一致/结构连续/待确认登记 | 文字表达问题 |
| 代码一致性 C1-C6 | 锚点反查/接口一致/数据结构/出站调用/覆盖留痕/mermaid校验 | 代码与文档矛盾 |

**已有能力的边界**：C1能发现"函数删了/改名了"，E3能发现"术语不一致"。但发现不了以下问题——

### 2.3 增强1：置信度概率评分（来源：A-MAC）

**补什么**：spec-asset-audit的扣分制是确定性的（命中就扣10分），不能表达"有多大概率是错的"。加概率置信度排序。

```
声明: "delete()同步删除实例"

spec-asset-audit C1: delete()函数在 → 通过(不扣分)
→ spec-asset-audit判"已基线"

🆕置信度评分:
  代码一致性: 文档说"同步", 代码返回CompletableFuture → 0.1
  AST对齐: 函数结构变了 → 0.4
  API签名: 返回类型void→CompletableFuture → 0.3
  C = 0.5×0.1 + 0.3×0.4 + 0.2×0.3 = 0.23
  
  置信度0.23 → 极低 → 标"存疑" → 给田主

→ spec-asset-audit判通过但置信度判存疑 → 以置信度为准
```

**效果**：1000条中，~750条高置信(≥0.8)自动标"大概率正确"跳过，~250条低置信标"存疑"给田主。

### 2.4 增强2：跨commit合成检测（来源：StructMem）

**补什么**：C1能发现"函数删了"但发现不了"流程中间插了新步骤"。

```
声明: "登录流程3步: Login → onControlTcpConnected → 事件处理"

spec-asset-audit C1: Login()在✓ onControlTcpConnected()在✓ → 通过

🆕跨commit合成:
  分析代码diff: Login和onControlTcpConnected之间新增了registerChannel()
  实际流程: 4步(多了registerChannel)
  文档3步 vs 实际4步 → ⚠️ 不完整 → 标"存疑"
  
  → C1发现不了的，跨commit合成发现
```

**效果**：+60条隐性不完整标"存疑"。

### 2.5 增强3：领域语义校验（来源：领域大模型 + StructMem Ω）

**补什么**：E3只查"术语一致不一致"，不查"业务语义对不对"。

```
声明: "Muen SDK创建Chrome实例"

spec-asset-audit E3: "Muen SDK"在lexicon有登记 → 术语一致 → 通过

🆕领域语义校验:
  调用领域大模型: "Muen SDK在业务中的正确定位是什么?"
  领域大模型推理: "Muen SDK是可信虚拟化平台(安全沙箱)，不是Chrome启动器"
  文档说"创建Chrome" → 实际是"隔离运行Chrome" → 🔤 语义偏差 → 标"存疑"
  
  → E3发现不了的，领域大模型发现
```

**效果**：+50条语义偏差标"存疑"。

### 2.6 增强4：跨来源冲突检测（来源：LatticeMind）

**补什么**：spec-asset-audit只审docs/资产，不处理来源A/B/C之间的矛盾。

```
来源A(逆向): "BrowserCloserTask关闭过期实例" (权重45)
来源B(领域大模型): "回收不活跃实例" (权重60)

🆕跨来源冲突检测:
  代码AST: delete()含upload+remove+report → 是"回收"
  → 来源B(60) > 来源A(45) → 来源A标"存疑"(术语偏差)
  → 生成修正建议给田主确认
```

**效果**：+40条来源间冲突标"存疑"。

### 2.7 存疑识别总效果

| 检测器 | 来源 | 发现什么 | 新增存疑条数 |
|--------|------|---------|------------|
| spec-asset-audit E/C | 已有 | 表达问题+代码矛盾 | ~100条 |
| 🆕置信度评分 | A-MAC | 概率排序，高置信跳过 | (过滤750条) |
| 🆕跨commit合成 | StructMem | 流程链断裂 | +60条 |
| 🆕领域语义校验 | 领域大模型 | 业务语义偏差 | +50条 |
| 🆕跨来源冲突 | LatticeMind | 来源间矛盾 | +40条 |
| **最终存疑清单** | | | **~250条** |

**田主收到的审核清单**：每条附带"文档说了什么/代码现状是什么/差异类型/置信度/修正建议"，每条30秒确认。**从4人天降到1人天，75%降低。**

## 三、阶段3：资产检索召回增强

> **解决的问题**：资产检索召回不准确（整体策略第3点）
>
> **目标**：在众多文档中提供正确的召回信息

### 3.1 问题分析

当前检索（specgo已有或通用RAG）的问题：

| 问题 | 原因 | 后果 |
|------|------|------|
| 召回不全 | 只用文本相似度，语义相关但文字不同的召回不到 | "热迁移"查不到"实例迁移" |
| 召回不准 | 不区分来源可信度，低可信的排在前面 | AI逆向的"关闭"排在领域大模型的"回收"前面 |
| 召回太慢 | 简单查询和复杂查询用同一种检索方式 | 查个函数签名也要跑完整检索流程 |
| 无法定位代码 | 检索到文档但不知道对应哪个代码文件 | 看到"delete()同步删除"但不知道在哪个文件 |

### 3.2 增强1：双路径自适应检索（来源：RF-Mem）

**原理**：先做探测检索算相似度均值和熵。高熟悉（证据集中）走快路径直接返回；低熟悉（证据分散）走慢路径聚类扩展。

```
场景1: Agent查"delete()的返回类型是什么?"
  探测: s̄=0.85(高), H=0.08(低) → 证据集中
  → 快路径: 直接top-K, 3ms
  → 返回: "delete()返回CompletableFuture<Void>"

场景2: Agent查"浏览器实例从创建到销毁完整流程?"
  探测: s̄=0.38(低), H=0.35(高) → 证据分散
  → 慢路径: KMeans聚3簇(创建/运行/销毁)
    → α混合生成3个回忆查询分头检索
    → beam search选优 → 12ms
  → 返回: 跨多模块完整流程链

场景3: Agent查"核保模块的体检规则怎么实现的?"
  探测: s̄=0.52(中), H=0.22(中) → 中间地带
  → 熵裁决: H>τ → 走慢路径
  → 聚类扩展找到相关代码和文档
```

**效果**：简单查询3ms（不降），复杂查询12ms但召回更全。

### 3.3 增强2：多来源加权排序（来源：LatticeMind 证据权重）

**原理**：检索结果同时返回来自不同来源的条目，按来源可信度排序，高可信优先。

```
查询: "BrowserCloserTask的回收规则是什么?"

检索结果(按可信度排序):
  1. [来源B-领域大模型] 置信度0.85 ⭐最高优先
     "BrowserCloserTask回收不活跃实例(含心跳过期+远端不活跃)"
  
  2. [来源A-逆向] 置信度0.15 ❌低置信(和代码矛盾)
     "BrowserCloserTask关闭过期实例"
     冲突提示: 与来源B术语偏差("关闭"vs"回收")
  
  3. [来源C-外挂文档] 置信度0.40 ⚠️(版本可能过时)
     "BrowserCheckTask定期检查实例状态"

→ Agent优先用来源B(最可信)
→ 来源A附带冲突提示，不会被误导
```

**效果**：检索结果附带可信度排序和冲突提示，Agent不被低可信信息误导。

### 3.4 增强3：语义+结构双索引（来源：StructMem + A-MAC）

**原理**：不只靠文本相似度，增加AST结构指纹和代码位置索引。

| 索引类型 | 怎么建 | 解决什么 |
|---------|--------|---------|
| 语义索引(已有) | 文本嵌入向量 | 文字相似的召回 |
| 🆕AST结构指纹 | tree-sitter解析AST做哈希 | "同一段代码模式不同变量名"的召回（文本不相似但结构相同） |
| 🆕代码位置索引 | 文档声明的代码文件路径→文档映射 | "查到代码文件直接定位描述它的文档" |

```
场景: Agent查"哪里有实例回收逻辑?"

文本相似度检索: 搜"回收" → 只找到写了"回收"的文档
  → 漏了写"关闭"的文档(虽然实际描述的是同一件事)

🆕AST结构指纹检索:
  delete()的AST结构哈希 → 找到所有结构相同的实现
  → 不管文档写的是"回收"还是"关闭"，只要代码结构相同都召回

🆕代码位置索引:
  Agent在代码里看到BrowserCloserTask.java
  → 代码位置索引: BrowserCloserTask.java → rules-browser.md
  → 直接返回描述这个代码文件的文档
```

**效果**：召回率提升——语义相关但文字不同的、结构相同变量名不同的、有代码位置映射的，都能召回。
