# POC 评估数据集选型方案

---

## 一、评估能力矩阵：先确定"评什么"

POC 有 7 个核心能力需要评估，每个能力的评估方式不同：

| 能力 | 来源论文 | 评估核心问题 | 需要什么数据集 |
|------|---------|------------|-------------|
| ① 事件提取质量 | StructMem | 三视角提取(Φ/Ψ/Ω)是否准确？ | 带标注的commit序列 |
| ② 准入控制精度 | A-MAC | 该存的存了没？该拒的拒了没？ | commit + "该不该存"标签 |
| ③ 冲突解决正确率 | LatticeMind | 新旧冲突时谁赢对了没？ | 构造冲突对(旧文档 vs 新代码) |
| ④ 跨事件合成质量 | StructMem | 合成的演进链/规则链对不对？ | 多commit序列 + 人工标注的演进脉络 |
| ⑤ 双路径检索效果 | RF-Mem | 快路径够不够快？慢路径够不够全？ | 编码任务查询集 + 期望检索结果 |
| ⑥ 领域知识自进化 | StructMem+HORMA | 术语表更新对不对？技能精炼有没有提升？ | 领域术语字典 + 编码任务前后对比 |
| ⑦ 端到端编码效果 | 全部融合 | 有记忆比无记忆编码效果好多少？ | 跨session编码任务集 + 期望答案 |

**关键原则**：不追求单一数据集覆盖全部能力——每个能力用**最适合的数据集**评估，最后用端到端任务验证整体效果。

## 二、公开数据集选型

### 2.1 可直接使用的公开数据集

| 数据集 | 规模 | 适配能力 | 怎么用 |
|--------|------|---------|--------|
| **SWE-bench** (Jimenez et al.) | 2294个GitHub issue→patch | ⑦端到端 | 有记忆vs无记忆的任务通过率对比 |
| **SWE-bench-lite** | 300个子集 | ⑦端到端 | 轻量验证，跑得快 |
| **CommitChronicles** | 17万条commit message | ①提取质量 | 批量跑三视角提取，人工抽检100条 |
| **RepoBench** | 仓库级代码理解 | ⑤检索效果 | 跨文件函数检索的recall@K |
| **LoCoMo** | 10段长对话519个QA | ⑤检索(适配) | 改造成"代码对话"版本：把对话换成commit+review讨论 |
| **ConflictBank** (Su et al.) | 多源矛盾证据 | ③冲突解决 | label-blind协议直接用：A/B/C三个来源谁对 |

### 2.2 公开数据集的适配改造

公开数据集不是为编码记忆场景设计的，需要**适配改造**：

**LoCoMo → 代码对话版**：
```
原版: 用户和Agent的多轮对话 → 记忆QA
改造: 开发者和Code Reviewer的多轮讨论 → 代码记忆QA
     "上次review说这个函数要加null check，加了吗？"
     "三个commit前重构了支付模块，现在的调用入口是哪个？"
```

**SWE-bench → 记忆增强版**：
```
原版: 给issue描述 → 生成patch → 测试通过率
改造: 同一个issue，分两种条件跑:
  A: 无记忆(原始opencode)
  B: 有记忆(POC记忆系统注入历史commit知识)
  对比A/B的通过率和步数
```

**ConflictBank → 代码冲突版**：
```
原版: 三个来源说不同的事实 → 谁对
改造: 三个来源 = 代码commit / 技术文档 / 人工笔记 → 代码证据该赢
  "文档说审批走邮件" vs "代码说审批走request_permissions" vs "笔记说审批走OA系统"
  → 代码证据(weight=100)应取代文档(12)和笔记(12)
```

### 2.3 公开数据集选型决策

| 评估能力 | 公开数据集 | 是否需要改造 | 改造工作量 |
|---------|-----------|------------|-----------|
| ① 提取质量 | CommitChronicles | 是(加三视角标注) | 中(100条人工标注) |
| ② 准入控制 | 无直接对应 | 自建 | 大 |
| ③ 冲突解决 | ConflictBank | 是(改成代码场景) | 中 |
| ④ 跨事件合成 | 无直接对应 | 自建 | 大 |
| ⑤ 检索效果 | RepoBench + LoCoMo改造 | 是 | 中 |
| ⑥ 领域自进化 | 无直接对应 | 自建 | 大 |
| ⑦ 端到端 | SWE-bench/SWE-bench-lite | 是(加记忆对比) | 小 |

**结论**：公开数据集覆盖①③⑤⑦四项，②④⑥需要自建。自建数据集是POC最大的工作量。

## 三、自建数据集设计

### 3.1 代码仓库选择

POC 需要一个**有业务领域知识、有较长Git历史、有文档与代码不一致问题**的真实仓库：

| 候选仓库 | 领域 | 优势 | 劣势 |
|---------|------|------|------|
| **保险核心系统(内部)** | 保险业务 | 领域知识丰富、业务规则明确 | 需要内部脱敏 |
| **开源保险系统** | 保险 | 可公开 | 可能不够真实 |
| **银行风控系统(内部)** | 金融风控 | 合规约束多、规则变化频繁 | 需要内部脱敏 |
| **Spring Boot Petclinic** | 通用 | 有完整Git历史、文档+代码 | 无业务领域知识 |
| **OWASP示例项目** | 安全 | 有安全规则和合规约束 | 领域偏窄 |

**推荐方案**：双仓库策略——

- **仓库A（垂域验证）**：内部保险/银行系统仓库（脱敏后），验证领域知识自进化、业务规则演进链
- **仓库B（基线验证）**：Spring Boot Petclinic 或类似开源项目，验证通用记忆能力、与公开benchmark对齐

### 3.2 自建数据集1：Commit标注集（评估①②）

**目标**：验证三视角提取质量 + 准入控制精度

**构建方法**：
```
Step 1: 从仓库A取过去6个月全部commit（约200-500条）
Step 2: 领域专家抽取50条commit做详细标注:
        - 每条commit的期望Φ(代码事实)条目
        - 每条commit的期望Ψ(工程关系)条目  
        - 每条commit的期望Ω(领域语义)条目
        - 每条commit"该不该存进记忆"的标签(是/否)
        - 如果该存，属于哪种类型(持久知识/半持久/临时)
Step 3: POC系统对50条commit跑三视角提取+准入评分
Step 4: 对比系统输出与人工标注
```

**标注模板**：
```json
{
  "commit_hash": "a1b2c3d",
  "commit_message": "feat: 核保模块新增高龄体检规则",
  "expected_facts": [
    "UnderwritingRule.java新增requireMedicalExam方法",
    "参数: age >= 60"
  ],
  "expected_relations": [
    "UnderwritingService.evaluate()调用链新增分支",
    "影响: 核保通过率会降低"
  ],
  "expected_domain": [
    "业务规则: 高龄投保人(≥60岁)需额外体检",
    "业务流程: 核保",
    "风险等级: 中",
    "合规约束: 待确认"
  ],
  "should_admit": true,
  "admit_type": "persistent",
  "admit_reason": "业务规则持久有效，跨任务复用"
}
```

**评估指标**：
- 提取精确率：系统输出条目中正确的比例
- 提取召回率：人工标注条目中被系统输出的比例
- Ω视角领域术语识别率：领域语义条目中术语被正确标注的比例
- 准入精确率/召回率：该存的存了没、该拒的拒了没

### 3.3 自建数据集2：冲突对集（评估③）

**目标**：验证冲突检测和证据加权取代的正确性

**构建方法**：
```
Step 1: 从仓库A中找"代码与文档不一致"的案例
        - 人工笔记/文档说X
        - 后来的commit代码说Y
        - X和Y矛盾

Step 2: 构造30个冲突对，覆盖:
        - 代码 vs 文档 (10对): 代码应赢
        - 代码 vs 代码 (10对): 新commit应赢
        - 文档 vs 笔记 (5对): 文档应赢
        - 多源矛盾 (5对): code-change应赢human-note

Step 3: POC系统对每个冲突对跑冲突解决
Step 4: 对比系统裁决与期望裁决
```

**标注模板**：
```json
{
  "conflict_id": "C001",
  "existing_memory": {
    "content": "审批走邮件流程",
    "evidence_type": "human-note",
    "timestamp": "2026-01-15"
  },
  "new_claim": {
    "content": "审批走request_permissions工具",
    "evidence_type": "code-change",
    "git_commit": "e4f5g6h",
    "timestamp": "2026-03-01"
  },
  "expected_winner": "new_claim",
  "expected_reason": "code-change(60+40=100) > human-note(12)",
  "expected_loser_status": "Superseded"
}
```

### 3.4 自建数据集3：跨事件查询集（评估④⑤）

**目标**：验证跨commit合成质量和双路径检索效果

**构建方法**：
```
Step 1: 从仓库A取3个Sprint的commit历史（约30-50条commit）
Step 2: 跑POC跨事件合成，产出合成记忆
Step 3: 领域专家设计30个查询，分三类:
        
        简单查询(10个) — 应走快路径:
          "UnderwritingService.checkAgeRule的方法签名是什么?"
          "ClaimCalculator的calculatePayout有几个参数?"
          期望: 直接命中原子条目
        
        跨commit查询(10个) — 应走慢路径:
          "核保体检规则是怎么演化的?"
          "理赔计算公式从年初到现在改了几次?每次改了什么?"
          期望: 命中合成记忆(业务规则演进链)
        
        跨模块查询(10个) — 应走慢路径+聚类扩展:
          "保单从投保到理赔经过哪些模块?每个模块的关键函数是什么?"
          "最近3个Sprint哪些模块改动最多?改动原因是什么?"
          期望: 聚类扩展后命中多个模块的条目

Step 4: POC系统对30个查询跑双路径检索
Step 5: 对比检索结果与期望结果
```

**评估指标**：
- 快/慢路径切换正确率：查询该走快路径时走了快路径、该走慢时走了慢
- Recall@K：期望结果中有多少被检索到
- 合成记忆命中率：跨commit查询命中合成记忆的比例
- 检索延迟：快路径p50、慢路径p95

### 3.5 自建数据集4：领域术语集（评估⑥）

**目标**：验证领域知识层自进化的效果

**构建方法**：
```
Step 1: 领域专家整理初始术语表(50-100个术语):
        "保单批改": "投保人信息变更"
        "核保规则": "保险公司评估风险的决定规则"
        "赔付系数": "理赔金额的计算因子"
        ...

Step 2: 将初始术语表注入POC的/domain/glossary.json
Step 3: 跑3个Sprint的commit历史，让POC自进化术语表
Step 4: 领域专家检查POC产出的:
        - 新增术语: 是否正确? 是否遗漏?
        - 更新术语: 定义变更是否准确?
        - 删除术语(如有): 是否合理?

Step 5: 对比"有领域知识层注入"vs"无注入"的提取质量
```

**评估指标**：
- 术语识别率：commit中领域术语被正确标注的比例
- 术语表自进化精确率：新术语中正确的比例
- 有/无注入对比：Ω视角条目质量提升多少

### 3.6 自建数据集5：跨session编码任务集（评估⑦）

**目标**：验证有记忆比无记忆编码效果好多少

**构建方法**：
```
Step 1: 设计20个编码任务，分4类:
        
        Bug修复(5个): 
          "核保模块的NullPointerException, 跟上次修的类似"
          → 需要回忆Bug修复模式(合成记忆)
        
        功能扩展(5个):
          "给理赔计算加一个新的免赔额规则"
          → 需要回忆现有理赔计算逻辑(原子条目)
        
        架构理解(5个):
          "投保到出单的完整调用链是什么?"
          → 需要跨模块推理(慢路径检索)
        
        过时文档修正(5个):
          "文档说审批走邮件, 但代码已经改了, 帮我更新文档"
          → 需要冲突检测(代码vs文档)

Step 2: 每个任务跑两遍:
        A: 无记忆(opencode原始能力)
        B: 有记忆(POC记忆系统注入)

Step 3: 评估:
        - 任务完成率(通过测试/人工评判)
        - 交互步数(有记忆应更少步)
        - 代码质量(LLM-as-judge)
        - 领域术语使用准确率
```

## 四、Ground Truth 构建策略

### 4.1 各数据集的Ground Truth来源

| 数据集 | Ground Truth来源 | 标注成本 |
|--------|-----------------|---------|
| Commit标注集(①②) | 领域专家+资深开发人工标注50条 | ~2人天 |
| 冲突对集(③) | 从真实代码vs文档不一致中构造30对 | ~1人天 |
| 跨事件查询集(④⑤) | 领域专家设计30个查询+期望结果 | ~2人天 |
| 领域术语集(⑥) | 领域专家整理初始术语表50-100个 | ~1人天 |
| 跨session任务集(⑦) | 设计20个编码任务+测试用例 | ~3人天 |
| **总计** | | **~9人天** |

### 4.2 标注一致性保障

- **双标注+仲裁**：Commit标注集由2位领域专家独立标注，分歧由第3人仲裁
- **LLM-as-judge交叉验证**：用3个不同LLM(GPT/Qwen/DeepSeek)做自动评估，Fleiss' κ > 0.8才算可靠（参考StructMem论文方法）
- **增量标注**：先标10条跑通流程，确认标注模板合理后再标剩余40条

## 五、评估指标体系总览

### 5.1 按能力分

| 能力 | 指标 | 数据集 | 目标值 |
|------|------|--------|-------|
| ① 提取质量 | Φ/Ψ/Ω精确率&召回率 | Commit标注集50条 | ≥85% |
| ② 准入控制 | 准入精确率&召回率 | Commit标注集50条 | ≥80% |
| ③ 冲突解决 | 裁决正确率 | 冲突对集30对 | ≥90% |
| ④ 跨事件合成 | 合成记忆命中率 | 跨事件查询集30个 | ≥75% |
| ⑤ 双路径检索 | Recall@60 + 快慢路径切换率 | 跨事件查询集30个 | R@60≥85%, 切换≥90% |
| ⑥ 领域自进化 | 术语识别率 + 自进化精确率 | 领域术语集 | 识别≥85%, 进化≥80% |
| ⑦ 端到端 | 任务通过率提升 + 步数减少 | 跨session任务集20个 | 通过率+15%, 步数-30% |
| 效率 | 检索延迟p50/p95 | 全部查询 | p50≤5ms, p95≤15ms |
| 效率 | Token成本 | 全部任务 | ≤基线22% |

### 5.2 对比实验矩阵

| 实验组 | 提取 | 准入 | 冲突 | 合成 | 检索 | 领域 | 验证目标 |
|--------|------|------|------|------|------|------|---------|
| A: 无记忆 | - | - | - | - | - | - | 基线 |
| B: 扁平检索 | ✓ | ✗ | ✗ | ✗ | Dense top-K | ✗ | 有记忆但无结构 |
| C: +准入 | ✓ | ✓ | ✗ | ✗ | Dense top-K | ✗ | A-MAC增益 |
| D: +冲突 | ✓ | ✓ | ✓ | ✗ | Dense top-K | ✗ | LatticeMind增益 |
| E: +合成 | ✓ | ✓ | ✓ | ✓ | Dense top-K | ✗ | StructMem合成增益 |
| F: +双路径 | ✓ | ✓ | ✓ | ✓ | RF-Mem双路径 | ✗ | RF-Mem增益 |
| G: +领域 | ✓ | ✓ | ✓ | ✓ | RF-Mem双路径 | ✓ | 领域知识层增益 |
| H: 完整POC | ✓ | ✓ | ✓ | ✓ | RF-Mem双路径 | ✓+技能精炼 | 全部融合 |

**关键对比**：A vs H（整体增益）、B vs G（结构化增益）、G vs H（技能精炼增益）

### 5.3 消融实验指标

| 移除模块 | 预期影响指标 | 验证什么 |
|---------|------------|---------|
| 移除Ω视角 | 术语识别率 85%→40% | 领域语义层价值 |
| 移除置信度三重验证(退化为ROUGE-L) | 冲突解决正确率 90%→65% | 编码场景C因子升级价值 |
| 移除冲突解决 | 过时文档干扰率 0%→30% | LatticeMind价值 |
| 移除跨事件合成 | 多跳查询命中率 75%→40% | StructMem合成价值 |
| 移除慢路径(只走快) | 跨模块查询召回 85%→50% | RF-Mem慢路径价值 |
| 移除快路径(只走慢) | 简单查询延迟 5ms→12ms | RF-Mem快路径价值 |
| 移除技能精炼 | 后期任务无提升 | HORMA自进化价值 |

## 六、数据集规模与可行性评估

| 数据集 | 样本量 | 标注人天 | 跑通时间 | 风险 |
|--------|--------|---------|---------|------|
| Commit标注集 | 50条 | 2 | 1天 | 低 |
| 冲突对集 | 30对 | 1 | 0.5天 | 低 |
| 跨事件查询集 | 30个 | 2 | 1天 | 中(期望结果标注) |
| 领域术语集 | 50-100个 | 1 | 0.5天 | 低 |
| 跨session任务集 | 20个 | 3 | 2天 | 中(任务设计) |
| SWE-bench-lite | 300个 | 0 | 1天 | 低(公开) |
| **总计** | — | **9人天** | **~6天** | — |

**结论**：9人天标注成本 + 6天跑通时间，对于一个POC验证来说是**合理且可行**的。最关键的瓶颈是跨session任务集的设计——需要精心设计20个能体现记忆价值的任务。

## 七、最终推荐方案

### 7.1 数据集选型决策

```
公开数据集(零标注成本):
  └─ SWE-bench-lite (300个) → 端到端基线对比

自建数据集(9人天):
  ├─ Commit标注集 (50条) → 提取质量 + 准入控制
  ├─ 冲突对集 (30对) → 冲突解决
  ├─ 跨事件查询集 (30个) → 合成质量 + 检索效果
  ├─ 领域术语集 (50-100个) → 领域知识自进化
  └─ 跨session任务集 (20个) → 端到端记忆增益

代码仓库:
  ├─ 仓库A: 内部保险/银行系统(脱敏) → 垂域验证
  └─ 仓库B: Spring Boot Petclinic → 基线对齐
```

### 7.2 评估流程

```
Phase 1-2: 用Commit标注集验证提取+准入 (第1-2周)
Phase 3: 用冲突对集验证冲突解决 (第3周)
Phase 4: 用跨事件查询集验证合成+检索 (第4周)
Phase 5: 用领域术语集验证自进化 (第5周)
Phase 6: 用跨session任务集+SWE-bench-lite验证端到端 (第6周)
```

### 7.3 成功标准

POC验证成功的最低标准（必须全部达成）：
- [ ] 提取精确率 ≥ 85%（三视角提取可信）
- [ ] 冲突解决正确率 ≥ 90%（代码自动取代旧文档）
- [ ] 跨commit查询命中合成记忆 ≥ 75%（跨事件合成有效）
- [ ] 有记忆比无记忆任务通过率提升 ≥ 15%（整体有价值）
- [ ] 检索延迟 p50 ≤ 5ms（不阻塞opencode）

达成以上标准后，可进入下一阶段：将POC扩展为生产级插件。
