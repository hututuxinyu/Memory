### 你的文档已经有的三个关键信息

读完几个代表性文件后，发现你的文档目录天然具备 StructMem 需要的三个要素：

**1. 每个文档都有"生成时间"**

```markdown
> 生成时间：2026-08-18
```

这就是 StructMem 需要的**时间锚点 τ_doc**——文档是8月18日生成的，之后代码的改动都可能让文档过时。

**2. 每个文档都有"代码位置映射"**

```markdown
| 参与方 | 代码位置 |
| browser-gateway | browser-gateway/src/main/java/com/huawei/browsergateway/sdk/ClientImpl.java |
| api | browser-proxy/browser_proxy/api/browser.py |
```

这就是 StructMem 需要的**模块/函数映射**——文档的每条声明已经标注了对应的代码文件，直接知道该去检查哪个文件。

**3. lexicon/ 目录已经是领域术语表**

```markdown
| 术语 | 释义 | 代码命名映射 |
| 预开浏览器请求（InitBrowserRequest） | 预开浏览器实例的HTTP请求模型 | InitBrowserRequest.java |
| 厂商（factory） | 终端设备厂商 | factory, InitBrowserRequest.java |
```

这就是 StructMem 领域知识层的**冷启动数据源**——不需要从零建术语表，你的 `0-biz/lexicon/` 已经有了。

## 二、StructMem 能解决你的什么问题

### 问题1：文档生成于8月18日，代码之后改了哪些？文档还准吗？

**你的痛点**：`interaction-model-create-browser.md` 8月18日生成的，写的是"通过Playwright以persistent context方式启动Chrome"。但9月、10月代码可能改了启动方式，文档自己不知道。

**StructMem 怎么接入**：

```
Step 1: 读取文档的"生成时间" τ_doc = 2026-08-18

Step 2: 搜索 τ_doc 之后修改了相关代码文件的commit:
        文档标注的代码位置: browser-proxy/browser_proxy/api/browser.py
        → git log --since=2026-08-18 -- browser_proxy/api/browser.py
        → 找到9月、10月的3次commit

Step 3: 对每次commit做三视角提取:
        commit f8a3b2c (9月):
          左栏(事实): create_browser() 的启动参数从 persistent_context 改为 launch()
          右栏(关系): 被 BrowserWrapper.__init__ 调用, 影响实例注册逻辑
          Ω(领域): 浏览器启动方式从"持久上下文"改为"独立启动"

Step 4: StructMem记忆库现在有"代码真相":
        "9月commit f8a3b2c把启动方式从persistent_context改成了launch()"
```

**到这里 StructMem 做完了它的事**——提取出了代码真相。但**文档过没过时还没判断**——那是 LatticeMind 的活。

**LatticeMind 接力**：

```
LatticeMind 拿 StructMem 的代码真相去和文档比对:
  文档说: "通过Playwright以persistent context方式启动Chrome"
  代码说: "改为launch()独立启动"
  → ❌ 冲突！
  证据权重: code-change(60)+git-bonus(40)=100 >> reverse-doc(12)
  → 文档过时，标记人工复核
```

### 问题2：改了一个模块，哪些文档受影响？

**你的痛点**：改了 `browser-proxy/browser_proxy/api/browser.py`，但不知道 `docs/` 里哪些文档描述了这个文件的逻辑——是 `interaction-model-create-browser.md`？还是 `rules-browser.md`？还是 `data-model-browser-wrapper.md`？

**StructMem 怎么解决**：

StructMem 的三视角提取中，**右栏（关系条目）记录的就是"改了这个模块影响谁"**：

```
commit f8a3b2c 的关系条目:
  EventTransport.send() 被3个文档描述:
    ① interaction-model-create-browser.md §主链路 (描述了启动流程)
    ② rules-browser.md §create-chrome-fail-cleanup (描述了失败清理规则)
    ③ data-model-browser-wrapper.md (描述了BrowserWrapper数据结构)
  
  → 改了 browser.py 要同步检查这3个文档
```

**人话**：你的文档目录是35个交互模型+6个规则+10个数据模型+...共上百个文件。改了一处代码要手动翻哪些文档受影响？StructMem 的右栏（关系条目）直接告诉你"这次改动涉及哪3个文档"。

### 问题3：业务规则散落在多个文档里，没有统一视图

**你的痛点**：`rules-browser.md` 里有"容量阈值""锁超时降级""心跳过期回收"等规则，但这些规则的代码实现在不同文件里（`ChromeSetImpl.java`、`RemoteImpl.java`、`BrowserCloserTask.java`）。改了其中一个文件的代码，要判断哪些规则受影响，得人工逐条对照。

**StructMem 怎么解决**：

StructMem 跨commit合成可以产出**业务规则演进链**——把散落在多个commit中的规则变更连起来：

```
合成记忆: "浏览器实例回收规则演进"
──────────────────────────────────────
8月(文档生成时): 三种回收规则:
  ① 容量阈值: userChromeMap.size() >= cap → 拒绝创建
  ② 锁超时: tryLock(120s)超时 → 复用或拒绝
  ③ 心跳过期: nanoTime - heartbeats > ttl → 删除实例

9月 commit x1: 心跳TTL从配置值改为动态计算(根据设备类型)
  → 规则③变化: 心跳过期判断逻辑变了
  → rules-browser.md 中 browser-closer-if-expired 规则可能过时

10月 commit x2: 新增"CSE远端不活跃"判断条件
  → 规则③又变: 从单一心跳判断变为"心跳过期 OR 远端不活跃"
  → rules-browser.md 中 browser-closer-is-active 规则是新增的，文档没有
──────────────────────────────────────
```

**人话**：文档8月写了3种回收规则，9月改了规则③的逻辑，10月又加了新规则③b。文档描述的是8月的三种，但实际已经变成四种了——StructMem 合成记忆告诉你"规则③在9月改了、10月新增了③b"。

### 问题4：领域术语表不随代码更新

**你的痛点**：`0-biz/lexicon/` 里的术语表是8月18日整理的。如果9月代码里新增了"WebSocket Boss-Worker模式"（见 `concurrency-guidelines-websocket-boss-worker.md`），术语表里没有这个词，opencode 遇到就不知道是什么。

**StructMem 怎么解决**：

StructMem 的领域知识层是**自进化**的——从 commit 提取的领域语义条目(Ω)中发现新术语时，自动更新术语表：

```
8月冷启动: 
  从 docs/0-biz/lexicon/ 导入初始术语表(约50个术语)
  → .opencode/memory/domain/glossary.json

9月 commit x1 的Ω条目:
  "新增 WebSocket Boss-Worker 模式: Netty的Boss线程接受连接,Worker线程处理IO"
  → StructMem 发现术语表中没有"WebSocket Boss-Worker"
  → 自动添加到术语表

10月 commit x2 的Ω条目:
  "BrowserCheckTask 检查周期从1800000ms调整为600000ms"
  → StructMem 发现术语表中"BrowserCheckTask"的释义需要更新
  → 自动更新: 检查周期默认1800000ms → 600000ms(application.yaml配置)
```

**人话**：术语表8月建好后就不动了，但代码一直在加新概念。StructMem 从 commit 中发现新术语自动补进去——术语表越用越全，不需要人工维护。

## 五、诚实回答：StructMem 单独够不够

| 你要的效果 | StructMem单独够吗 | 还需要什么 |
|-----------|------------------|-----------|
| opencode不被过时文档误导 | ✅ 够 | StructMem提取的代码真相直接注入opencode |
| 改代码时知道影响哪些文档 | ✅ 够 | StructMem关系条目记录了文档-代码映射 |
| 产出文档里没有的演进脉络 | ✅ 够 | StructMem跨commit合成 |
| 术语表随代码更新 | ✅ 够 | StructMem领域知识层自进化 |
| **自动标出哪20%文档过时** | ❌ 不够 | 需要 LatticeMind 冲突检测+A-MAC置信度 |
| **自动更新过时文档** | ❌ 不够 | 需要HORMA技能精炼+人工确认 |

**结论**：StructMem 解决"让opencode用活真相而非死文档"的问题，但"自动识别文档中哪20%是错的"需要 StructMem + LatticeMind + A-MAC 三者配合。你的文档目录天然适合接入——生成时间、代码位置映射、术语表都现成了。
