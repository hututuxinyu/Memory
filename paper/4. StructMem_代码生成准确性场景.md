# StructMem 提升代码生成准确性的场景示例（非文档过时类）

> 除了"文档没跟上"之外，StructMem 的结构化记忆还能在以下场景提升代码生成准确性。

---

## 场景一：跨模块依赖感知——改共享代码不破坏调用方

### 需求

> "给 `ChromeSet.delete()` 加一个审计日志，记录谁删的、删了哪个实例。"

### 没有 StructMem 时

opencode 读 `ChromeSet` 代码，看到 `delete(String userId)` 方法，直接改：

```java
public void delete(String userId) {
    logger.info("Deleting browser instance for user: {}", userId);  // 新增审计日志
    UserChrome chrome = map.remove(userId);
    if (chrome != null) {
        chrome.cleanup();
    }
}
```

**问题**：`delete()` 被3个调用方调用，每个调用方对返回值的期望不同：

| 调用方 | 期望 | opencode不知道 |
|--------|------|----------------|
| `BrowserCloserTask` | 调delete后继续遍历下一个，不关心返回值 | 如果加了审计日志导致delete变慢，定时任务周期可能超时 |
| `BrowserCheckTask` | 批量调用delete，期望同步返回 | 如果日志写了文件IO，批量删除变慢 |
| `RemoteImpl` | 创建失败时调用delete做清理，期望快速返回 | 如果delete里加了chrome.cleanup()可能阻塞 |

opencode 不知道这些调用方的期望，加的审计日志可能破坏性能约定。

### 有 StructMem 时

StructMem 记忆库的**右栏（关系条目）**记录了 delete 的调用关系：

```
记忆: ChromeSet.delete() 的关系条目
──────────────────────────────────────
delete(userId) 被3个调用方调用:
  ① BrowserCloserTask: 定时回收, 批量调用, 要求快速返回
  ② BrowserCheckTask: 健康检查后批量删除, 同步调用
  ③ RemoteImpl: 创建失败清理, 要求快速返回不阻塞

调用方约定: 三个调用方都期望delete()是快速同步操作
──────────────────────────────────────
```

opencode 看到这条记忆后：

> "delete() 被3个调用方调用，都期望快速同步返回。审计日志不能在delete里同步写文件——改成异步写或者只写内存buffer。"

```java
// 有记忆的opencode生成的代码
private final AuditLogBuffer auditBuffer = new AuditLogBuffer();  // 异步缓冲

public void delete(String userId) {
    auditBuffer.append("DELETE", userId, Thread.currentThread().getName());  // 内存缓冲，不阻塞
    UserChrome chrome = map.remove(userId);
    if (chrome != null) {
        chrome.cleanup();
    }
}
```

**差异**：审计日志写成内存缓冲而非同步文件IO——因为记忆告诉opencode"3个调用方都要求快速返回"。

## 场景二：架构模式一致性——用对的模式而非常见的模式

### 需求

> "加一个新的定时任务，每隔5分钟检查一次浏览器实例的内存使用，超过阈值就告警。"

### 没有 StructMem 时

opencode 按最常见的Spring模式写：

```java
@Component
public class MemoryCheckTask {
    @Scheduled(fixedRate = 300000)  // Spring @Scheduled
    public void checkMemory() {
        // ...
    }
}
```

**问题**：这个项目**不用 Spring @Scheduled**——所有定时任务用的是 `ScheduledExecutorService`（见 `0-tech/concurrency-guidelines/`）。混用两种定时机制会导致：
- 线程池不统一，无法统一管控生命周期
- `@PreDestroy` 关闭顺序不一致
- 配置管理不统一（一个用yaml，一个用注解硬编码）

### 有 StructMem 时

StructMem 领域知识层注入的术语表里有：

```
术语表:
  "定时任务" → 本项目统一使用 ScheduledExecutorService
  禁止使用: Spring @Scheduled 注解
  原因: 统一线程池管理, @PreDestroy有序关闭, 配置统一走yaml
──────────────────────────────────────
```

合成记忆里有架构决策演进：

```
合成记忆: "定时任务架构决策"
──────────────────────────────────────
项目确立了 ScheduledExecutorService 模式:
  - @PostConstruct 中创建 scheduler
  - scheduleAtFixedRate 执行任务
  - @PreDestroy 中 scheduler.shutdown()
  - 周期配置走 browsergw.scheduled.* yaml key
  现有实现: BrowserCheckTask, BrowserCloserTask, TcpChannelMonitor
──────────────────────────────────────
```

opencode 看到记忆后：

> "这个项目统一用 ScheduledExecutorService，不用 @Scheduled。我参考 BrowserCheckTask 的写法："

```java
// 有记忆的opencode生成的代码
public class MemoryCheckTask {
    private ScheduledExecutorService scheduler;
    private final long period;
    
    @PostConstruct
    public void init() {
        scheduler = Executors.newSingleThreadScheduledExecutor();
        scheduler.scheduleAtFixedRate(this::checkMemory, 0, period, TimeUnit.MILLISECONDS);
    }
    
    @PreDestroy
    public void destroy() {
        scheduler.shutdown();
    }
    // ... 配置走 browsergw.scheduled.memory-check-period
}
```

**差异**：用 `ScheduledExecutorService` 而非 `@Scheduled`——因为记忆告诉opencode项目统一的定时任务模式。

## 场景三：业务规则一致性——新代码遵守已有规则

### 需求

> "加一个批量删除浏览器实例的接口：DELETE /api/browsers/batch"

### 没有 StructMem 时

opencode 写了个简单的批量删除：

```java
@DeleteMapping("/browsers/batch")
public Result<Void> batchDeleteBrowsers(@RequestBody List<String> userIds) {
    for (String userId : userIds) {
        chromeSet.delete(userId);
    }
    return Result.success();
}
```

**问题**：违反了至少4条已有业务规则（见 `0-biz/rules/rules-browser.md`）：

| 违反的规则 | 后果 |
|-----------|------|
| 没获取用户锁 `tryLock` | 并发删除可能和创建请求冲突 |
| 没检查实例状态 | 可能删了一个正在重建中的实例 |
| 没触发用户数据上传 | 用户数据丢失 |
| 没上报用量 | 计费数据不准 |

### 有 StructMem 时

StructMem 记忆库里有业务规则相关条目：

```
记忆: 浏览器实例删除的业务规则
──────────────────────────────────────
删除实例前必须:
  ① 获取用户锁 tryLock(120s) → 防止并发创建/删除冲突
  ② 检查实例状态 → OPEN_ERROR/PAGE_CONTROL_ERROR/REOPEN要重建而非删除
  ③ 触发用户数据上传 → delete()内部先uploadUserData再remove
  ④ 上报用量 → 用量统计计费
  
规则来源: rules-browser.md + commit历史
  delete-chrome-fail-cleanup: 删除时要回滚清理
  browser-closer-if-expired: 过期实例删除要上报用量
──────────────────────────────────────
```

opencode 看到记忆后：

> "批量删除不能直接循环删——每条删除都要获取用户锁、检查状态、确保数据上传。我参考已有的单条删除逻辑："

```java
@DeleteMapping("/browsers/batch")
public Result<BatchDeleteResult> batchDeleteBrowsers(@RequestBody List<String> userIds) {
    List<String> deleted = new ArrayList<>();
    List<String> skipped = new ArrayList<>();
    
    for (String userId : userIds) {
        // ① 获取用户锁
        if (!lockManager.tryLock(userId, LOCK_TIMEOUT_SECONDS)) {
            skipped.add(userId + ": lock timeout");
            continue;
        }
        try {
            UserChrome chrome = chromeSet.get(userId);
            // ② 检查实例状态
            if (chrome == null || chrome.getStatus() == BrowserStatus.REOPEN) {
                skipped.add(userId + ": not exists or reopening");
                continue;
            }
            // ③ delete内部会先uploadUserData再remove
            // ④ delete内部会上报用量
            chromeSet.delete(userId);
            deleted.add(userId);
        } finally {
            lockManager.unlock(userId);
        }
    }
    return Result.success(new BatchDeleteResult(deleted, skipped));
}
```

**差异**：加了锁、状态检查、数据上传、用量上报——因为记忆告诉opencode"删除实例有4条业务规则必须遵守"。

## 场景四：API复用——用已有接口而非重新造轮子

### 需求

> "加一个功能：检查浏览器实例是否健康，不健康就重启。"

### 没有 StructMem 时

opencode 从头写健康检查逻辑：

```java
public boolean isBrowserHealthy(String userId) {
    UserChrome chrome = chromeSet.get(userId);
    if (chrome == null) return false;
    
    // 自己实现健康检查
    ChromeDriver driver = chrome.getChromeDriver();
    try {
        driver.executeScript("return document.readyState");
        return true;
    } catch (Exception e) {
        return false;
    }
}
```

**问题**：项目里**已经有**健康检查逻辑——`BrowserCheckTask` 通过 `DriverClient.browser().healthCheck()` 做的。opencode 不知道，又造了一个轮子，而且这个轮子和已有的检查逻辑不一致（一个查document.readyState，一个查proxyContextId）。

### 有 StructMem 时

StructMem 合成记忆里有：

```
合成记忆: "浏览器健康检查已有实现"
──────────────────────────────────────
BrowserCheckTask.checkBrowsers() 已实现健康检查:
  - 调用 DriverClient.browser().healthCheck() 获取健康结果
  - 检查 result.isSuccess()
  - 不健康的实例: proxyContextId 命中 result.getErrContexts()
  - 处理: chromeSet.delete(userId) 删除异常实例
──────────────────────────────────────
```

opencode 看到记忆后：

> "项目里 BrowserCheckTask 已经有健康检查逻辑了，用的是 `DriverClient.browser().healthCheck()`。我不重新写，直接复用："

```java
public void checkAndRestart(String userId) {
    // 复用已有的健康检查API
    Type.HealthCheckResult result = client.browser().healthCheck();
    if (result.isSuccess()) {
        return;  // 全部健康
    }
    UserChrome chrome = chromeSet.get(userId);
    if (chrome == null) return;
    
    String proxyContextId = chrome.getChromeDriver().getProxyContextId();
    if (result.getErrContexts().contains(proxyContextId)) {
        // 不健康，复用已有的删除+重建逻辑
        chromeSet.deleteForRestart(userId);  // 已有方法: 删旧建新不断TCP
    }
}
```

**差异**：复用已有的 `healthCheck()` 和 `deleteForRestart()` 而非重新造轮子——因为记忆告诉opencode"项目已有这个能力"。

## 场景五：Bug修复模式复用——同类Bug用同类修法

### 需求

> "修一个Bug：WebSocket断线重连后偶发消息丢失。"

### 没有 StructMem 时

opencode 从头分析WebSocket代码，找断线重连逻辑，分析消息丢失原因，写修复。

### 有 StructMem 时

StructMem 事件层记忆里有类似的Bug修复记录：

```
记忆: 2个月前修的类似Bug
──────────────────────────────────────
commit x9y8z7w (2月前):
  Bug: TcpChannel 断线重连后偶发事件丢失
  根因: 重连成功前的缓冲消息在重连后被丢弃
  修复模式: 
    ① 重连前缓存待发消息到LinkedBlockingQueue
    ② 重连成功后flush缓存队列
    ③ 超过队列容量(1000)时丢弃旧消息(防OOM)
  代码: TcpChannel.reconnect() 加了messageBuffer逻辑
──────────────────────────────────────
```

opencode 看到记忆后：

> "2个月前TCP通道也有类似的断线重连消息丢失Bug，根因是重连前的缓冲消息被丢弃，修复模式是加LinkedBlockingQueue缓存+flush。WebSocket可能也是同样的问题。我来看看WebSocket的重连逻辑……确实，重连后没flush旧消息。用同样的模式修："

```java
// 有记忆的opencode: 复用2月前的Bug修复模式
private final LinkedBlockingQueue<String> pendingMessages = new LinkedBlockingQueue<>(1000);

public void onReconnected() {
    // flush重连前缓存的消息
    String msg;
    while ((msg = pendingMessages.poll()) != null) {
        send(msg);
    }
}

public void send(String message) {
    if (!isConnected()) {
        if (!pendingMessages.offer(message)) {
            // 队列满，丢弃最旧的消息防OOM
            pendingMessages.poll();
            pendingMessages.offer(message);
        }
        return;
    }
    // ... 正常发送
}
```

**差异**：直接复用2个月前的修复模式而非从头分析——因为记忆告诉opencode"类似Bug之前怎么修的"。

## 总结：StructMem 提升准确性的5个维度

| 维度 | 无记忆的后果 | 有StructMem记忆的效果 | 记忆来源 |
|------|------------|---------------------|---------|
| **跨模块依赖感知** | 改共享代码破坏调用方约定 | 知道3个调用方期望，不破坏 | 右栏(关系条目) |
| **架构模式一致** | 用常见的Spring模式而非项目模式 | 用项目统一的ScheduledExecutorService | 合成记忆+领域知识层 |
| **业务规则一致** | 新接口违反已有4条业务规则 | 加锁、状态检查、数据上传、用量上报 | 合成记忆(业务规则) |
| **API复用** | 重新造健康检查轮子 | 复用已有的healthCheck()+deleteForRestart() | 合成记忆(已有实现) |
| **Bug模式复用** | 同类Bug从头分析 | 直接套用2月前的修复模式 | 事件层(历史Bug修复) |

**核心一句话**：StructMem 让 opencode 从"每次从头写代码"变成"基于项目历史经验写代码"——知道改了什么会影响谁、项目用什么模式、业务有什么规则、已有什么能力、同类Bug怎么修过。这才是准确性的来源——不是文档准不准，而是**代码演进过程中的经验能不能被复用**。
