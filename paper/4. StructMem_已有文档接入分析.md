# StructMem 与已有文档目录的接入分析

> **核心问题**：已有软件资产文档目录（docs/），80%正确20%过时。StructMem 能否解决这个问题？能解决哪些？不能解决哪些？

---

## 一、你现在面临的真实痛点

你有 SBG 云手机的代码仓 + 一份软件资产文档目录。具体痛点是：

### 痛点1：文档和代码的关系是"断"的

文档目录里写着"§3 输入事件转发：通过UDP通道转发"。但代码里 `EventTransport.java` 上个月已从 UDP 改成了 WebSocket。**文档自己不知道自己过时了**——它不会主动告诉你"我描述的那个代码已经被改了"。

opencode 读这份文档时，信以为真，以为还是 UDP，然后基于错误信息做决策。

### 痛点2：文档是"平面"的，没有关系

文档目录里"§3 输入事件转发"和"§2 视频流传输"是两个独立文件。但实际上它们共享 `EventTransport` 模块——改了传输协议两个文档都受影响。**文档之间没有"关系"连接**，改了一处不知道要同步更新哪些文档。

### 痛点3：文档是"静态快照"，没有演进

文档描述的是某个时间点的代码状态。但代码一直在改——3个月改了60次commit。文档**不知道自己描述的功能经历了什么变化**。opencode 读文档只看到"现在的样子"，不知道"为什么变成这样、之前是什么样的"。

### 痛点4：业务术语散落在文档各处

"热迁移""GPU状态不一致""实例亲和性"这些业务术语散落在文档各章节里，没有统一的术语表。opencode 每次遇到都要猜含义。

## 二、StructMem 能解决哪些？不能解决哪些？

| 痛点 | StructMem能解决吗 | 怎么解决 | 不能解决的部分 |
|------|------------------|---------|--------------|
| ①文档不知道自己过时了 | **部分能** | commit时间戳和文档生成时间对比，能发现"文档生成之后代码改了" | 但"改了之后文档描述还对不对"需要LatticeMind做冲突检测 |
| ②文档之间没有关系 | **能** | 三视角提取的右栏(关系条目)记录"改了这个模块影响哪些文档" | — |
| ③文档没有演进历史 | **能** | 跨commit合成产出"架构演进脉络/Bug修复模式" | — |
| ④业务术语散落 | **能** | 领域知识层(Ω视角)提取并自进化术语表 | — |

### 关键诚实回答

**StructMem 不能直接解决"80%正确20%错误"的检测问题。**

StructMem 做的是：**在你的文档目录之上，建一层"活的"结构化记忆**——它持续从commit中提取新知识、合成演进脉络、维护术语表。这层记忆是"活的"（随代码更新），而你的文档目录是"死的"（静态快照）。

"80%正确20%错误"的检测，需要的是 **LatticeMind 的冲突检测**（代码证据 vs 文档声明的矛盾比对）+ **A-MAC 的置信度评分**。StructMem 提供的是**让冲突检测成为可能的"结构化底座"**——没有 StructMem 提取的"代码事实+关系+领域语义"，LatticeMind 没有东西可比。

**换句话说**：

- StructMem 负责把代码的"真相"持续提取出来 → "代码现在到底是什么样子"
- 你的文档目录是"3个月前的快照" → "文档以为代码是什么样子"
- LatticeMind 负责拿 StructMem 的"真相"去和文档的"快照"比对 → "哪里对不上"
- A-MAC 负责给每条文档打置信度 → "对不上的有多严重"

## 三、你已有文档目录后，StructMem 怎么接入

**不是替代你的文档，而是在文档之上建一层"活记忆"**：

```
你的文档目录 (docs/)          ← 静态快照, 80%正确
  │
  │ StructMem 在这层之上建记忆
  │
  ├─ 事件层 (.opencode/memory/events/)
  │    每次commit自动提取:
  │    左栏(事实): 代码改了什么
  │    右栏(关系): 影响了哪些模块/文档
  │    Ω(领域): 涉及什么业务规则
  │    锚定: commit_hash + 时间戳
  │
  ├─ 合成层 (.opencode/memory/synthesis/)
  │    定期合成:
  │    架构演进脉络 (文档没有的)
  │    Bug修复模式 (文档没有的)
  │    业务规则变更链 (文档没有的)
  │
  └─ 领域层 (.opencode/memory/domain/)
       从你的docs/glossary.md冷启动
       随commit自动补充新术语
```

### 具体接入步骤

**Step 1：冷启动——用现有文档初始化领域知识层**

你的 `docs/` 目录里已有的业务术语、架构说明，批量提取到 StructMem 的领域知识层。不需要从头建——**你已有的文档就是冷启动数据源**。

```
docs/glossary.md → 提取术语 → .opencode/memory/domain/glossary.json
docs/architecture.md → 提取架构决策 → .opencode/memory/synthesis/
docs/business-rules.md → 提取业务规则 → .opencode/memory/domain/rules.json
```

**Step 2：历史回填——用Git历史初始化事件层**

对过去3个月的60次commit批量跑三视角提取，积累初始记忆库。这样 opencode 下次启动时记忆库不是空的。

**Step 3：持续运行——每次commit自动提取**

opencode 每次执行 `git commit` 后自动触发提取，记忆库持续增长。文档目录保持不动（作为静态参考），记忆库是"活"的增量。

**Step 4：定期合成——Sprint结束批量总结**

每个Sprint结束触发跨commit合成，产出文档目录里没有的演进脉络。

**Step 5：过时检测（需要LatticeMind）——定期拿记忆去和文档比对**

定期拿 StructMem 提取的"代码真相"去和 `docs/` 里的"文档快照"比对，标出不一致的条目。这才是解决"20%错误"的那一步。

## 四、具体例子

你的 `docs/transport.md` 写着：

> 触控事件通过UDP通道转发到云侧，每个事件包256字节。

### StructMem 做了什么

```
commit f8a3b2c 触发三视角提取:

左栏(事实): EventTransport.send() 从DatagramSocket改为WebSocket
右栏(关系): EventTransport被3个模块调用(触控/视频/音频)
Ω(领域): 传输协议从UDP改为WebSocket, 影响网络自适应策略
锚定: commit_hash=f8a3b2c, 时间=2月前

→ 写入 .opencode/memory/events/f8a3b2c/
```

### StructMem 没做什么

StructMem **没有**拿这个事实去和 `docs/transport.md` 比对说"你的文档说UDP但代码已改成WebSocket了"——那是 LatticeMind 的冲突检测做的事。

### StructMem 的价值在哪

1. **opencode 下次session时**：检索到记忆"传输协议改成了WebSocket"→ opencode 知道当前真相是WebSocket，不会被 `docs/transport.md` 里写的UDP误导
2. **合成记忆产出**：跨commit合成出"传输协议演进：UDP→WebSocket(2月前)→WebSocket+断线重连(1月前)" → `docs/` 里没有这个演进脉络
3. **领域知识层更新**：术语表新增"WebSocket传输"→ 下次提取时LLM能识别这个术语

### LatticeMind 补上了什么

```
LatticeMind 定期拿StructMem的"代码真相"去和docs/比对:

StructMem记忆: "EventTransport现在用WebSocket" (证据权重: code-change=100)
文档docs/transport.md: "通过UDP通道转发" (证据权重: reverse-doc=12)

比对: 矛盾！
裁决: 代码证据(100) >> 文档证据(12) → 文档过时
标记: ❌ docs/transport.md §1 置信度=0.14 → 需人工复核
```

**StructMem 提供"代码真相"，LatticeMind 拿真相去和文档比对发现矛盾。**两者配合才能解决"20%错误"的问题。

## 五、五篇论文在"已有文档"场景下的分工

| 论文 | 在已有文档场景中的角色 | 提供什么 | 解决什么 |
|------|---------------------|---------|---------|
| **StructMem** | 持续提取"代码真相" | 三视角条目(事实+关系+领域语义) | 让opencode用"活的真相"而非"死的文档"做决策 |
| **LatticeMind** | 拿"代码真相"去和"文档快照"比对 | 冲突检测+证据加权取代 | 发现文档中20%过时的条目 |
| **A-MAC** | 给每条文档声明打置信度 | 五维评分(效用/置信度/新颖性/近因性/类型先验) | 区分"严重过时"和"轻微不一致" |
| **HORMA** | 组织记忆和文档的可导航结构 | 文件系统层级+技能精炼 | 让opencode能导航式检索而非扁平搜索 |
| **RF-Mem** | 检索时自适应快慢路径 | 熵门控+聚类扩展 | 简单查询快速命中、复杂查询深入挖掘 |

**关键关系**：StructMem 是"底座"——没有它提取的代码真相，LatticeMind 没有东西可比；没有它的领域知识层，A-MAC 的类型先验分不了类。但 StructMem 单独不解决"20%错误检测"——它只提供"真相"，检测矛盾需要 LatticeMind。

---

## 六、一句话总结

**你已有的文档目录是"3个月前的快照"，StructMem 在它之上建一层"持续从commit提取的活记忆"**。StructMem 的价值是让 opencode 用"活的代码真相"做决策而不是用"死的文档快照"，并产出文档里没有的演进脉络和术语表。

但**"自动识别文档中哪20%是错的"这件事，StructMem 只提供了一半能力（提取代码真相），另一半（拿真相去和文档比对发现矛盾）需要 LatticeMind 的冲突检测**。所以 POC 方案是五篇论文融合的，不是 StructMem 单独能搞定的。
