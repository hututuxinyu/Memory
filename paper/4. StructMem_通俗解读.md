# StructMem 通俗版：编码 Agent 场景下的结构化记忆

> 用 opencode（编码 Agent）的真实工作场景，讲清楚 StructMem 的结构化记忆到底怎么起效果。不说数学，只讲故事。

---

## 场景设定：opencode 维护 SBG 云手机系统

你是开发者，每天用 opencode 做云手机系统的编码任务。opencode 每次开一个新 session，session 之间没有记忆——昨天修的Bug、上周重构的架构、上个月学到的业务规则，今天全忘了。

**没有结构化记忆的 opencode**：每次新 session 都像新来的实习生——不知道昨天干了什么，不知道项目架构演进历史，不知道"实例迁移"和"实例销毁"有什么区别。

**有了 StructMem 结构化记忆的 opencode**：每次新 session 自动加载历史记忆——知道上次修了什么Bug、知道架构怎么演进的、知道业务术语的含义。

下面用 **5个真实编码场景** 讲清楚结构化记忆怎么起效果。

---

## 场景一：Bug 修复模式复用

### 没有记忆时

**周一 session**：你让 opencode 修一个Bug：

> 你："云手机实例迁移时偶尔报 NullPointerException"

opencode 从头分析：读 `InstanceMigrationService.java`，发现 `getInstance()` 可能返回 null 但调用方没判空，加了 null check，修好了。

**周三 session**：又来了一个类似Bug：

> 你："视频流切换时也报 NullPointerException"

opencode 又从头分析：读 `VideoStreamSwitcher.java`，发现 `getStream()` 可能返回 null 但调用方没判空……又是同样的问题，又要分析一遍。

### 有了 StructMem 记忆时

**周一 session** 修完迁移Bug后，opencode 自动写了一条记忆：

```
事件: 修了 InstanceMigrationService 的 NPE
左栏(事实): getInstance() 返回null未判空, 加了null check
右栏(关系): getInstance()被迁移流程的多个步骤调用, 
            根因是实例状态查询服务不稳定时返回null
──────────────────────────────────────
锚定: commit a1b2c3d, 周一
```

**周三 session** 启动时，opencode 自动检索到这条记忆。当你说"视频流切换也报 NPE"时：

> opencode："这和周一修的迁移NPE是同一类问题——`getStream()` 可能返回 null 未判空。上次根因是状态查询服务不稳定时返回 null。我建议先检查 `StreamService.getStream()` 是否有同样的 null 返回路径，如果是的话，用上次同样的 null check 模式修复。"

**结构化记忆起了什么作用**：opencode 不是从头分析，而是**复用了上次修同类Bug的经验**——知道根因模式（状态服务返回null），知道修复模式（加null check），直接套用。省了10分钟的重新分析时间。

## 场景二：架构演进理解

### 没有记忆时

**新 session**，你让 opencode 加一个功能：

> 你："给云手机实例加一个'暂停'功能"

opencode 读代码，发现 `InstanceService` 里只有 `create()`、`destroy()`、`migrate()` 三个方法，没有 `pause()`。但它不知道**为什么**架构是这样的——能不能直接加个 `pause()` 方法？跟现有架构一致吗？它只能猜。

### 有了 StructMem 记忆时

opencode session 启动时检索记忆库，找到一条**合成记忆**（跨commit合并产出的）：

```
合成记忆: "实例管理架构演进"
──────────────────────────────────────
3个月前(commit x9y8z7w): 
  InstanceService 从单体拆分, 原来所有操作在一个类里
  
2个月前(commit a1b2c3d): 
  确立了三个核心操作: create/destroy/migrate
  架构决策: 不加pause/resume, 因为云手机不支持挂起
  理由: 底层KVM虚拟化不支持暂停后恢复GPU状态
  
1个月前(commit e4f5g6h):
  迁移逻辑从destroy+create改为热迁移, 不需要暂停
──────────────────────────────────────
```

opencode 看到这条记忆后：

> opencode："我看了一下架构历史。3个月前架构确立了只有 create/destroy/migrate 三个操作，当时明确决定不加 pause/resume，因为底层 KVM 不支持暂停后恢复 GPU 状态。你想加的'暂停'功能是要在前端做暂停按钮（只断开连接不真正暂停实例），还是要底层真正支持？如果是前者我可以在 SessionController 加一个 disconnect 接口；如果是后者需要改虚拟化层，工作量大很多。"

**结构化记忆起了什么作用**：opencode **理解了架构决策的历史和原因**——不是只看到代码"现在长什么样"，还知道"为什么长这样"、"之前想过加pause但决定不加"、"因为KVM不支持"。这让 opencode 不会盲目加一个 `pause()` 方法破坏现有架构决策。

## 场景三：跨模块影响分析

### 没有记忆时

> 你："我把 EventTransport 的传输协议从 UDP 改成了 WebSocket，帮我检查一下其他模块有没有受影响"

opencode 需要从头分析：
1. grep "EventTransport" 全项目 → 找到 15 个引用文件
2. 逐个检查每个引用点
3. 不知道哪些引用是关键的、哪些是边缘的

### 有了 StructMem 记忆时

opencode 检索记忆库，找到 EventTransport 相关的**关系条目**（右栏记录的工程关系）：

```
记忆: EventTransport 相关关系条目
──────────────────────────────────────
commit f8a3b2c (2月前):
  事实: EventTransport.send() 从UDP改为WebSocket
  关系: EventTransport 被3个模块调用:
    ① InputEventForwarder → 转发触控事件 (高频, 实时性要求高)
    ② VideoStreamRelay → 转发视频帧 (高频, 带宽敏感)  
    ③ AudioSyncPipeline → 转发音频同步信号 (低频, 延迟容忍)
  
  影响评估: 
    ① 触控: WebSocket的重连延迟可能导致触控卡顿 → 需要加重连缓冲
    ② 视频: WebSocket的帧封装开销比UDP大 → 需要评估带宽影响  
    ③ 音频: 低频传输, 影响不大
──────────────────────────────────────
```

opencode 看到这条记忆后：

> opencode："上次改 EventTransport 时记录了它被3个模块调用。模块①触控转发是高频实时场景，WebSocket 重连延迟可能导致触控卡顿，建议加重连缓冲机制。模块②视频帧转发带宽敏感，WebSocket帧封装开销比UDP大约多4-8字节/帧，需要评估。模块③音频同步是低频的，影响不大。我建议先检查模块①的触控链路。"

**结构化记忆起了什么作用**：opencode **不需要从头 grep 全项目找引用关系**——记忆库的右栏（关系条目）已经记录了"EventTransport 被谁调用、各调用方的特点"。opencode 直接拿记忆里的影响评估，10秒回答，而不是花5分钟 grep + 分析。

## 场景四：业务术语理解

### 没有记忆时

> 你："检查一下'热迁移'逻辑有没有处理'GPU状态不一致'的情况"

opencode 不知道"热迁移"和"GPU状态不一致"在这个项目里的具体含义，只能猜——可能搜代码找"hot migration"或"gpu state"，但代码里可能用的中文注释或缩写，不一定匹配到。

### 有了 StructMem 记忆时

opencode 的记忆库里有**领域知识层**（自进化的术语表）：

```
领域知识层: .opencode/memory/domain/glossary.json
──────────────────────────────────────
"热迁移": 
  定义: 云手机实例在不中断用户连接的情况下从一台物理机迁移到另一台
  涉及模块: InstanceMigrationService.migrateHot()
  关键步骤: 1.内存状态同步 2.GPU状态快照 3.连接切换
  相关概念: "GPU状态不一致"

"GPU状态不一致":
  定义: 热迁移后目标机的GPU状态与源机不一致, 导致画面闪烁/花屏
  涉及模块: GpuStateManager.checkConsistency()
  已知风险: WebGL上下文丢失, 纹理丢失, 着色器需重建
──────────────────────────────────────
```

opencode 看到术语表后：

> opencode："'热迁移'在我们的代码里是 `InstanceMigrationService.migrateHot()` 方法，'GPU状态不一致'是指热迁移后目标机GPU状态与源机不一致的问题，涉及 `GpuStateManager.checkConsistency()`。我来检查这个方法的逻辑……发现它只检查了纹理一致性，没有检查WebGL上下文。根据术语表记录的已知风险'WebGL上下文丢失'，这里应该补一个WebGL上下文检查。"

**结构化记忆起了什么作用**：opencode **懂业务术语了**——不是靠猜，而是记忆库的领域知识层直接告诉它"热迁移"在代码里对应哪个方法、"GPU状态不一致"是什么意思、已知风险有哪些。这让 opencode 能做**领域语义级别的分析**，而不只是代码语法级别的搜索。

## 场景五：跨 session 的状态感知

### 没有记忆时

> 你（周二）："继续昨天的活，把音频同步模块的重构做完"

opencode 不知道"昨天"做了什么——新 session 是空白的。你得从头解释："昨天我开始重构 AudioSyncPipeline，把同步逻辑从同步等待改成了异步回调，改了一半还差 AudioBuffer 的部分没改完……"

### 有了 StructMem 记忆时

opencode session 启动时自动检索最近的记忆：

```
记忆: 昨天的编码事件
──────────────────────────────────────
commit p3q4r5s (昨天 17:30):
  事实: AudioSyncPipeline 从同步等待改为异步回调
    已改: AudioSyncPipeline.sync() → asyncSync()
    已改: AudioListener.onSync() 适配异步回调
    未改: AudioBuffer.waitForSync() ← 还在用旧的同步等待

  关系: AudioBuffer.waitForSync() 被 AudioSyncPipeline.asyncSync() 调用
        但 waitForSync() 是阻塞的, 与异步回调模式矛盾 → 需要改为非阻塞

  领域语义: 音频同步从"阻塞等待"架构改为"事件回调"架构
            属于架构决策演进, 非临时改动
──────────────────────────────────────
```

opencode 看到这条记忆后：

> opencode："昨天你在重构 AudioSyncPipeline，已经把 `sync()` 改成了 `asyncSync()`，也适配了 `AudioListener`。但 `AudioBuffer.waitForSync()` 还在用旧的阻塞等待方式，跟新的异步回调模式矛盾——它被 `asyncSync()` 调用但会阻塞。需要改成非阻塞的 `onSyncComplete` 回调。我来改这个。"

**结构化记忆起了什么作用**：opencode **跨 session 保持了上下文连续性**——知道昨天改了什么、改到哪了、还差什么。你不需要从头解释，直接说"继续昨天的活"就行。

## 结构化记忆的三个层级怎么协同

上面5个场景用到了记忆的不同层级。总结一下三层记忆各自起什么作用：

```
编码Agent工作流程
  │
  ├─ session启动 → 检索记忆注入上下文
  │    ├─ 原子条目层: "昨天改了什么"(细节) ───→ 场景五:跨session连续性
  │    ├─ 合成记忆层: "架构怎么演进的"(脉络) ─→ 场景二:架构演进理解
  │    └─ 领域知识层: "业务术语什么意思"(知识) → 场景四:业务术语理解
  │
  ├─ 编码工作中 → 检索相关记忆辅助决策
  │    └─ 关系条目(右栏): "改了这个模块影响谁" ─→ 场景三:跨模块影响分析
  │
  └─ session结束 → 提取记忆写入存储
       └─ 三视角提取: 事实+关系+领域语义 ───→ 场景一:Bug修复模式(下次复用)
```

| 记忆层 | 存什么 | 什么时候用 | 解决什么问题 |
|--------|--------|-----------|------------|
| **原子条目层** | 每次commit的代码事实+工程关系 | 查"具体改了什么" | 跨session连续性、跨模块影响分析 |
| **合成记忆层** | 跨commit的架构演进/Bug模式/规则链 | 查"怎么演变的" | 架构理解、Bug模式复用 |
| **领域知识层** | 术语表/规则字典/模块映射 | 提取时注入LLM | 业务术语理解、领域语义分析 |

**三层协同**：领域知识层让Agent"懂业务"→能提取出有业务含义的条目→条目积累后跨commit合成出演进脉络→脉络让Agent理解架构历史→下次编码任务时利用这些理解做更好的决策。

## 关键问题：这些记忆是怎么来的

**不是人工写的，是 opencode 在编码过程中自动提取的**。

每次 opencode 执行 `git commit` 后，自动触发三视角提取：

```
opencode 执行 git commit "fix: 触控事件NPE"
  │
  ├─ 左栏(事实): 从Git diff提取
  │    "InputEventForwarder.java: getInstance()加了null check"
  │
  ├─ 右栏(关系): 从AST分析提取
  │    "getInstance()被3个调用方使用: 触控/视频/音频"
  │    "根因: 实例状态查询服务不稳定时返回null"
  │
  └─ 领域语义: 从领域知识层辅助提取
       "Bug类型: NullPointerException"
       "涉及: 触控事件转发流程"
       "修复模式: 状态查询返回值判空"
  │
  └─ 锚定: commit_hash + 时间戳 → 写入 .opencode/memory/events/
```

**领域知识层也是自进化的**：如果合成记忆中出现了新术语（比如"热迁移""GPU状态不一致"），自动更新术语表。下次提取时LLM就能识别这些术语。

## 效果对比总结

| 编码任务 | 无记忆时opencode怎么做 | 有StructMem记忆后怎么做 | 节省 |
|---------|----------------------|----------------------|------|
| 修同类Bug | 从头读代码分析 | 复用上次Bug修复模式 | ~10分钟 |
| 理解架构决策 | 只看代码现状,不知道为什么 | 看合成记忆的架构演进脉络 | ~15分钟 |
| 跨模块影响检查 | grep全项目逐个分析 | 查记忆的关系条目直接知道 | ~5分钟 |
| 理解业务术语 | 猜或问人 | 查领域知识层术语表 | ~5分钟 |
| 跨session继续工作 | 从头解释上下文 | 自动加载上次记忆 | ~10分钟 |

**一次编码任务平均节省10-15分钟**——对于每天做5-10个任务的编码Agent，一天节省1-2小时。

---

## 一句话总结

opencode 每次做 `git commit` 后自动提取"做了什么(事实)+影响了谁(关系)+业务含义(领域语义)"三层记忆，锚定到commit；定期把相关commit合在一起总结出"架构演进脉络/Bug修复模式/业务规则链"；下次session启动时自动检索这些记忆注入上下文——**让opencode从"每次失忆的实习生"变成"有项目经验的熟手"**。
