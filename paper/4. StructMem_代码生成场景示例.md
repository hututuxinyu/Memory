# StructMem 在复杂业务代码生成场景的应用示例

> 用 BrowserGateway 的真实业务场景，讲清楚 StructMem 的结构化记忆怎么让 opencode 生成代码的效果更好。

---

## 场景：给浏览器实例管理加一个"优雅停机"功能

### 你的需求

> "给 BrowserGateway 加一个优雅停机功能：收到停机信号时，不等用户主动断开，主动给所有活跃的浏览器实例发关闭通知，等它们上传完用户数据再退出。"

这个需求看起来简单，但它牵扯**多个模块的协作**：
- 要遍历所有活跃实例（`ChromeSet`）
- 要触发用户数据上传（`BrowserWrapper` 的数据上传逻辑）
- 要等上传完成再删除实例（`chromeSet.delete`）
- 要和已有的定时回收任务协调（`BrowserCloserTask`/`BrowserCheckTask`）
- 不能和已有的锁机制冲突（`tryLock`）
- 要处理超时兜底（不能无限等）

---

## 没有 StructMem 时 opencode 怎么做

opencode 新 session 启动，记忆空白。它读 `docs/` 目录的文档：

1. 读 `0-arch/interaction-model/interaction-model-create-browser.md` → 知道浏览器怎么创建的
2. 读 `0-biz/rules/rules-browser.md` → 知道有容量阈值、锁超时、心跳过期回收规则
3. 读 `0-tech/concurrency-guidelines/concurrency-guidelines-browser-check-task.md` → 知道BrowserCheckTask怎么做的

**但文档是8月18日生成的，之后代码改了3次**：
- 9月：`BrowserCloserTask` 新增了"CSE远端不活跃"判断（文档没有）
- 10月：`chromeSet.delete` 改成了异步的（文档说同步）
- 10月：新增了 `TcpChannelMonitor` 监控类（文档完全没有这个类）

opencode 基于过时文档写代码：

```python
# opencode 生成的代码（基于过时文档）
def graceful_shutdown():
    for user_id in chrome_set.get_all_user():
        chrome = chrome_set.get(user_id)
        if chrome is not None:
            chrome.upload_user_data()  # 文档说同步上传
            chrome_set.delete(user_id)  # 文档说同步删除
```

**问题**：
1. `chrome_set.delete` 已经改成异步了，这里同步调用会出问题
2. 没有处理 `TcpChannelMonitor` 的连接清理逻辑——新类文档没有
3. 没有考虑 `BrowserCloserTask` 可能同时在跑——并发冲突
4. `CSE远端不活跃`判断可能已经把某些实例删了——遍历时会踩空

opencode 不知道这些，因为文档没写，它也没记忆。

---

## 有 StructMem 时 opencode 怎么做

opencode 新 session 启动，自动检索记忆库。

### 记忆注入了什么

**事件层记忆**（从9月、10月的commit提取）：

```
commit a1b2c3d (9月) 三视角条目:
  左栏(事实): BrowserCloserTask 新增 isRemoteInactive() 判断
    代码: ub==null || browserInstance==null || 
          browserInstance!=config.getSelfAddr() || heartbeats==null
  右栏(关系): isRemoteInactive() 与本地心跳过期是"或"关系
    → 改了 chrome_set 可能导致遍历时实例已被异步删除
  Ω(领域): 浏览器实例回收规则从"单一心跳判断"变为"心跳OR远端不活跃"
  锚定: commit a1b2c3d, 9月

commit e4f5g6h (10月) 三视角条目:
  左栏(事实): ChromeSet.delete() 从同步改为异步
    代码: delete(userId) 现在返回 CompletableFuture
    新增: delete 内部先 uploadUserData() 再 remove()
  右栏(关系): delete() 被 BrowserCloserTask/BrowserCheckTask/
              RemoteImpl(创建失败清理) 三个调用方调用
    → 三处调用都需要适配异步返回
  Ω(领域): 实例删除语义从"同步即删"变为"异步上传后删"
  锚定: commit e4f5g6h, 10月

commit i7j8k9l (10月) 三视角条目:
  左栏(事实): 新增 TcpChannelMonitor 类
    代码: TcpChannelMonitor.monitor() 定期检查TCP通道状态
    新增方法: closeStaleChannel() 关闭过期通道
  右栏(关系): monitor() 被 @PostConstruct 启动
    closeStaleChannel() 需要在实例删除前调用
    → 否则TCP连接泄漏
  Ω(领域): 新增"TCP通道生命周期管理"概念
    实例关闭时必须先关TCP通道再删实例
  锚定: commit i7j8k9l, 10月
```

**合成层记忆**（跨commit合成的演进脉络）：

```
合成记忆: "浏览器实例关闭流程演进"
──────────────────────────────────────
8月(文档生成时): 关闭流程 = chromeSet.delete(userId) 同步删除
9月: 新增远端不活跃判断 → 实例可能在遍历时被异步删除
10月: delete()改为异步 → 需要等待Future完成
10月: 新增TcpChannelMonitor → 删除前必须先关TCP通道
──────────────────────────────────────
当前正确流程: 
  ① 先关TCP通道(TcpChannelMonitor.closeStaleChannel)
  ② 触发异步上传(chromeSet.delete返回Future)
  ③ 等Future完成(数据上传完毕)
  ④ 处理并发(BrowserCloserTask可能同时跑)
  ⑤ 超时兜底(不能无限等)
──────────────────────────────────────
```

**领域知识层注入**：

```
术语表: 
  "优雅停机" → 当前代码无此概念，需新增
  "TCP通道生命周期" → 实例关闭前必须先关TCP通道
  "异步删除" → chromeSet.delete返回CompletableFuture
  "远端不活跃" → CSE判断实例是否活跃的补充条件
```

### opencode 基于记忆生成代码

opencode 同时看到8月的文档（静态）+ 9-10月的记忆（活的）+ 合成记忆（演进脉络）：

> opencode："这个优雅停机需求涉及实例关闭流程。我查了一下记忆库，发现10月 `chromeSet.delete()` 已经改成了异步返回 `CompletableFuture`，而且新增了 `TcpChannelMonitor`，关闭实例前必须先关 TCP 通道，否则连接泄漏。另外 `BrowserCloserTask` 的远端不活跃判断可能导致遍历时实例被异步删除，需要做并发保护。我来写："

```java
@PreDestroy
public void gracefulShutdown() {
    logger.info("Graceful shutdown started");
    
    // ① 先关所有TCP通道（记忆: 10月新增TcpChannelMonitor，删除前必须关）
    tcpChannelMonitor.closeAllChannels();
    
    // ② 快照当前活跃实例列表（记忆: 9月新增远端不活跃判断，
    //    BrowserCloserTask可能同时删除实例，需要快照防并发）
    List<String> activeUsers = new ArrayList<>(chromeSet.getAllUser());
    
    // ③ 逐个触发异步删除（记忆: 10月delete改为异步，返回CompletableFuture）
    List<CompletableFuture<Void>> futures = new ArrayList<>();
    for (String userId : activeUsers) {
        UserChrome chrome = chromeSet.get(userId);
        if (chrome == null) {
            // 记忆: 9月远端不活跃判断可能已删除此实例
            continue;
        }
        // delete内部会先uploadUserData再remove
        futures.add(chromeSet.delete(userId));
    }
    
    // ④ 等待所有上传完成，带超时兜底
    try {
        CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
            .get(SHUTDOWN_TIMEOUT_SECONDS, TimeUnit.SECONDS);
        logger.info("All user data uploaded, shutdown complete");
    } catch (TimeoutException e) {
        // ⑤ 超时强制退出
        logger.warn("Shutdown timeout, force closing {} instances", 
            futures.stream().filter(f -> !f.isDone()).count());
        futures.forEach(f -> f.cancel(true));
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        logger.error("Shutdown interrupted");
    }
}
```

### 对比：有记忆 vs 无记忆

| 代码维度 | 无记忆（基于8月过时文档） | 有StructMem记忆 |
|---------|----------------------|----------------|
| TCP通道清理 | ❌ 没做（文档里没有TcpChannelMonitor） | ✅ 先关TCP通道再删实例 |
| 异步删除适配 | ❌ 同步调用delete（10月已改异步） | ✅ delete返回Future，等待完成 |
| 并发保护 | ❌ 直接遍历（9月新增的异步删除可能踩空） | ✅ 快照活跃实例列表+null检查 |
| 超时兜底 | ❌ 无限等待上传完成 | ✅ 带超时的allOf+强制退出 |
| 数据上传等待 | ❌ 文档说同步上传不需要等 | ✅ 等所有Future完成 |

**没有记忆的代码至少有4个bug**——TCP连接泄漏、异步返回值不处理、并发踩空、无限等待。这些bug不会在编译时暴露，而是在生产环境偶发——因为它们是代码演进过程中的变更，文档没跟上。

**有记忆的代码一次就对了**——因为 opencode 从记忆中知道了"delete改异步了""新增了TcpChannelMonitor""远端不活跃可能并发删除"。

## 这就是 StructMem 的价值

| 没有StructMem | 有StructMem |
|-------------|------------|
| opencode基于8月过时文档写代码 | opencode基于8月文档+9-10月记忆写代码 |
| 不知道delete改了异步 | 记忆里有事实"delete改成异步返回Future" |
| 不知道新增了TcpChannelMonitor | 记忆里有事实"新增TcpChannelMonitor，删除前必须关" |
| 不知道BrowserCloserTask可能并发删除 | 记忆里有关系"远端不活跃判断与本地心跳是OR关系" |
| 不知道当前正确的关闭流程 | 合成记忆有"正确流程:关TCP→触发异步→等Future→超时兜底" |
| **代码至少4个生产环境bug** | **代码一次就对了** |

**核心价值**：opencode 从"基于过时文档写代码"变成"基于代码真相写代码"。StructMem 持续从commit提取代码真相（事实+关系+领域语义），让opencode知道代码**现在**长什么样，而不是文档**3个月前**说长什么样。
