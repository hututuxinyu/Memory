## 一、ContextSniper 要解决什么问题？

### 先说大背景

LLM 编码 Agent 现在能修真实的 GitHub 仓库 issue 了（SWE-bench 这类基准就是干这个的）。但它们有个硬伤：**找不到证据就不会停，只会反复读**。一次补丁失败，就触发"读文件→试→失败→再读"的循环，token 一路烧，却不一定找到关键那几行。

这套流程之所以费，根源在 Agent 拿证据的方式太"原始"——直接 grep、读整文件、跑命令，把原始输出一股脑塞进上下文窗口。

### 现有做法的毛病

论文把现有路子归成三类，各自卡在哪：

| 路子                           | 代表                             | 卡在哪                                                                 |
| ------------------------------ | -------------------------------- | ---------------------------------------------------------------------- |
| **Agent 工具/Agent-计算机接口** | SWE-agent、AutoCodeRover、Agentless | 上下文跟"原始探索输出"绑死，没记忆、没预算控制                         |
| **Prompt/检索压缩**            | LLMLingua、RECOMP、Token Reducer | 在"内容已选好送进 prompt 之后"才压——选错了它救不回来                   |
| **工具输出过滤**               | RTK、Headroom、Bearing            | 能裁噪声，但不维护一份跟仓库同步的代码记忆，改完文件记忆就过时了       |

三类各改一环，**没人**在"原始仓库/运行时输出即将进入上下文"那个入口做拦截，同时还保持一份跟编辑同步的代码记忆。ContextSniper 就卡在这个位置。

### ContextSniper 的思路

一句话——**证据（evidence），不是压舱物（ballast）**。

它不替换宿主 Agent 的推理/编辑/验证循环，而是插在 Agent 和仓库之间当一层"上下文接入层"：把原始输出先当成"候选证据"，留下任务相关的代码和运行时信号、砍掉周围低价值区域，拼成一个紧凑的"证据包"再喂给模型。论文管这叫 **sniping（狙击）**——精准命中要害，不连片扫射。

核心原则：**retrieve broadly, expose narrowly（广检索，窄暴露）**。完整证据存在 prompt 外面，按多信号检索，只把该看的那几段返回去；每段都带仓库路径和行号，每条运行时信号都绑定产生它的那条命令/那次编辑。

## 二、ContextSniper 怎么存记忆？

### 两大族 + 三层抽象

记忆不是一本流水账，而是一个**存在 prompt 之外的本地记忆服务**（AGFS，Agent File System）。每个记忆节点是一个目录，存三种文本视图，对应三个检索层级：

| 层级   | 名字         | 存什么                                       | 作用                         |
| ------ | ------------ | -------------------------------------------- | ---------------------------- |
| **L0** | 紧凑摘要     | 短的、面向模型的摘要视图                     | 宽召回 + 长 read/命令的"裁剪后视图" |
| **L1** | 结构化概览   | 路径、行范围、符号、签名、ctags 符号类型、BM25 文档、图关系、工具名、命令状态、输出类型 | 路由和排序的元数据           |
| **L2** | 完整可恢复内容 | 源码块（带路径+行号头）/ 原始未过滤的 read 或命令输出 | 给 Agent 看的、可编辑/可恢复的真实证据 |

而**内容**分两族：

| 记忆族         | 来源                         | L2 具体存什么                                                     |
| -------------- | ---------------------------- | ----------------------------------------------------------------- |
| **代码记忆**   | 当前仓库快照                 | 源码块（带路径+行号头）；Python 用 AST 切分顶层 class/function/async，其它文件用重叠行窗口 |
| **行动记忆**   | 修复过程中产生的证据         | 原始未过滤的 read/命令输出（被裁剪后，原始版仍可恢复）             |

**为什么要分两族？** 代码记忆是"仓库长什么样"，行动记忆是"这次修复过程里发生了什么"。前者随仓库编辑刷新，后者记录每条 read/grep/命令/编辑的产出——它们要解决的问题不同，索引方式也不同。

### 为什么 L2 必须带路径和行号

这是论文反复强调的硬约束：返回给 Agent 的每段代码都必须**可定位、可编辑**。丢了行号、模糊了出处，Agent 就没法把补丁打到正确位置——通用摘要会"模糊 provenance、行号、可编辑性"，这正是简单压缩不能用的原因。

## 三、ContextSniper 怎么查记忆？

代码检索（`search_code`）是宿主 Agent 进代码记忆的主入口。它不返回原始 grep 输出，而是返回一小批带路径+行号的 L2 片段。

### 四路混合排序 + RRF 融合

混合排序器同时跑四路，再用**加权倒数排名融合（RRF）**融合（默认）：

| 检索路                 | 抓什么信号                                       |
| ---------------------- | ------------------------------------------------ |
| **语义嵌入**           | 问题的向量相似度                                 |
| **BM25 词项**          | 精确词法匹配                                     |
| **ctags 符号元数据**   | 符号名、符号类型、位置                           |
| **图关系**             | import / call / 包含 / 邻接文件的边              |

RRF 的道理和 MAGMA 一样：**不看分数只看排名**——一个片段在多路里都靠前，那它大概率重要。可配置时也支持加权分数求和。

如果索引检索太弱（召回不足），就**回退到 ripgrep 在工作区做文本搜索**——保证不漏。

### 自适应 Top-k：意图决定路预算

这是它和"固定返回 top-k"系统的关键差别。检索前先有个 planner 推断查询意图，按类型给各路分配预算：

| 查询类型                 | 偏重哪几路                          |
| ------------------------ | ------------------------------------ |
| **traceback 类**         | 路径、符号、grep 词项                |
| **行为类**               | 语义、图关系                          |
| **有状态调试轮**         | 从行动记忆里提升"最近碰过的文件"     |

流程是：planner 定类型+路预算 → 各路在 L0/L1/L2 上做种子检索 → 把有苗头的 L0/L1 展开成 L2 叶子 → 最终排序器按 URI 去重、按分排序 → 返回源码锚定的 L2 证据。返回数量 m 受"预算换 k"约束，不贪多。

### 一个直观例子

issue 报了个"某测试失败 + traceback"。Agent 调 `search_code`：

1. planner 判定是 traceback 类 → 给路径/符号/grep 路多拨预算；
2. 四路并行：BM25 命中 traceback 里的函数名、符号路命中它的定义位置、图路顺着 import/call 找到上游调用、语义路找到行为相近的函数；
3. RRF 融合 → 锁定 3-5 个 L2 片段，都带 `path.py:42-58` 这种头；
4. 若召回弱，ripgrep 兜底再捞一遍；
5. 最终 prune 掉分差大/重复文本，返回紧凑证据包。

Agent 拿到的是"这几行就是关键"，不是一整份 grep 的几百行结果。

## 四、ContextSniper 怎么过滤和同步？

光检索还不够——Agent 还会直接 read 文件、跑命令，这些**长输出**也得拦。这是"意图感知上下文门"（context gate）的活。

### 意图感知门：按动作类型保什么、砍什么

| 动作类型       | 保留                                                     | 砍掉                                   |
| -------------- | -------------------------------------------------------- | -------------------------------------- |
| **文件读**     | 请求区域、局部定义、import、class/function 体、邻接代码  | 长样板、无关区域                       |
| **测试/命令输出** | 命令行、退出码、断言消息、traceback、失败路径、简洁成功信号 | 重复日志、冗长尾巴                     |
| **状态**       | 改动的文件、碰过的符号、仓库状态、连接当前轮与早前证据的路径 | 不相关信号                             |

**关键设计——可恢复**：裁剪时把**原始完整输出**存进行动记忆的 L2，返回一个"已被 sniping"的标记。Agent 若觉得裁太狠了，可以按标记请求更宽的上下文。所以门是**保守**的——砍错比多花 token 危险，宁可留个回退口。

### 两阶段记忆-仓库同步

仓库不是静态的，Agent 边修边改。如果检索返回的是编辑前的旧版本函数，那紧凑上下文就成了"毒"。

| 阶段           | 何时跑                 | 干什么                                                                 |
| -------------- | ---------------------- | ---------------------------------------------------------------------- |
| **阶段一**     | 每次 Agent 动作后的运行时钩子 | 记录碰过的路径、返回区域、命令状态、失败输出、改动文件；编辑会校验路径、应用改动、派发该文件的记忆刷新；长 read/命令把裁剪视图和原始版都写进行动记忆 |
| **阶段二**     | 对话/任务边界（新 prompt 来时） | 跟工作树对账（看仓库 diff），改动的文件重新切块/刷新、删掉的片段失效、新相关区域可被后续检索命中 |

阶段二兜住"没走工具钩子"的改动，防止下一轮从过期记忆开始。**同步不是辅助记账，是让 sniping 在 Agent 改仓库后仍然可信的机制。**

## 五、实验结果

### 5.1 主结果（Table 2）——50 任务/条件配对对比

在 SWE-bench Lite 上，每条件各跑 50 个任务，宿主 Agent 的 baseline vs ContextSniper：

| 宿主 Agent   | 方法          | Res. Rate | Total Tok. | Cost     | Avg. Act. | Ctx. Act. | 相对 token |
| ------------ | ------------- | --------- | ---------- | -------- | --------- | --------- | ---------- |
| **OpenClaw** | Baseline      | 26.0%     | 67.80M     | $0.635   | 32.1      | 572       | —          |
|              | ContextSniper | 24.0%     | 32.91M     | $0.404   | 17.2      | 461       | **-51.5%** |
|              | 相对变化      | -2.0pp    | -51.5%     | -36.4%   | -46.4%    | -19.4%    |            |
| **Claude Code** | Baseline   | 32.0%     | 85.97M     | $15.09   | 29.9      | 791       | —          |
|              | ContextSniper | 30.0%     | 52.55M     | $10.97   | 19.2      | 522       | **-38.9%** |
|              | 相对变化      | -2.0pp    | -38.9%     | -27.3%   | -35.7%    | —         |            |

**亮点**：
- OpenClaw **token 减 51.5%**、成本降 36.4%、动作数降 46.4%；
- Claude Code **token 减 38.9%**、成本降 27.3%、动作数降 35.7%；
- 两个宿主下提交解决率都"基本不变"（各差 1 个任务，-2.0pp）。

**注意**：论文明确这是**效率主张，不是解决率提升主张**——验证器错误不均衡，不能下强结论。

## 六、失败案例分析（4.3）——什么时候反而更费 token？

那 5 个"反而更费"的任务最有信息量，分成两种模式：

| 模式                         | 典型任务                                              | 表现                                                            | 原因                                     |
| ---------------------------- | ----------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------- |
| **固定检索开销未被摊薄**     | pylint-7228、flask-5063、matplotlib-24265             | 动作数不变，只多 2-4 次 search_code，token 增 9.6%-17.3%        | 任务太短，检索层 setup + 搜索轮摊不开    |
| **召回不决/基线本就极短**    | seaborn-3407（+152.3%）、pytest-7168（+104.6%）       | 前者 6 次搜索仍没决断；后者基线只用 5 动作完成，ContextSniper 走 9 动作 | 检索 miss 导致继续搜，或短任务上叠加开销 |

**启示**：ContextSniper 在"早期检索能替代宽探索"时最强，在"短基线任务上叠开销"或"首包没命中决定性文件"时最弱。这恰恰标定了它的适用边界。

## 七、为什么主指标是 token，不是 solve-rate？

论文专门声明这点，原因有二：

1. **验证器错误不均衡**——OpenClaw baseline 验证通过 26 个、ContextSniper 通过 33 个；但解决率反而 26% vs 24%。验证器噪声使得解决率没法做强结论。
2. **定位不同**——ContextSniper 是"上下文接入层"基础设施，不替换宿主 Agent 的推理。它该被衡量的就是"同样解决能力下，能省多少上下文成本"。

所以论文用 token 总量、成本、动作数、上下文获取动作数这一组**效率指标**当主轴，解决率谨慎地作"基本不变"的旁证。这跟 MAGMA 用 LLM 评分替 F1 的逻辑同构：**指标要匹配系统能力声称的边界**。

## 八、与三类相关工作的位置关系

| 维度           | 现有系统                               | ContextSniper 的差异                                           |
| -------------- | -------------------------------------- | -------------------------------------------------------------- |
| **Agent 工具** | SWE-agent / AutoCodeRover / Agentless  | 上下文不跟原始探索输出绑死，有预算、有同步记忆                 |
| **Prompt 压缩** | LLMLingua / RECOMP / Token Reducer     | 在"内容进 prompt 之前"就拦截，而非选好之后再压                 |
| **输出过滤**   | RTK / Headroom / Bearing               | 不只裁噪，还维护一份跟仓库编辑同步的代码记忆                   |
| **跨任务记忆** | SWE-Exp / ExpeRepair / MemGovern / MEMCoder | 专注**任务时本地代码记忆**，不抢跨任务经验记忆的位置          |

一句话：**比 prompt 压缩早一步、比输出过滤多一份同步记忆、比 Agent 工具多一层预算控制**。

## 九、局限性（论文自陈）

| 局限                          | 通俗解释                                                                 |
| ----------------------------- | ------------------------------------------------------------------------ |
| **解决率结论受限**            | 需 SWE-bench Verified、更多任务/仓库、置信区间，才能把 token 节省和验证噪声分开 |
| **依赖检索与索引质量**        | 嵌入模型、切分策略、符号提取、结构边都影响命中；证据弱信号/跨异常文件/要跑测试才可见时，检索可能漏 |
| **sniping 过激风险**          | 砍太狠会丢有用证据；任务需要宽架构上下文时尤其危险                       |
| **缺"显式扩宽"机制**          | Agent 还需要更明确地请求更宽输出/展开缩短区/标重要文件的方式             |
| **未含提交历史记忆**           | prior changes 和 linked issue 可能揭示当前源检索漏掉的修复点             |
| **非完整 AntTrail 评测**      | 本文只评仓库级修复特化，不是完整跨域 AntTrail 引擎                       |

## 十、总结：ContextSniper 值得关注什么

### 一句话概括

**把"找证据"从 Agent 的推理循环里剥出来做成一层基础设施**——广检索（多路+RRF+ripgrep 兜底）、窄暴露（意图感知门裁噪）、记忆跟编辑同步（两阶段刷新），让 Agent 拿到的是"紧凑且源码锚定的证据包"而非一堆原始输出。

### 三个最值得借鉴的设计

| 设计                          | 为什么好                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------ |
| **两族 × 三层记忆层级**       | L0 宽召回、L1 路由、L2 可编辑可恢复——既省 token 又保 provenance，砍错还能回退   |
| **自适应 Top-k + 四路 RRF**   | 意图驱动的路预算让检索"对症下药"，ripgrep 兜底保召回                            |
| **意图感知门 + 两阶段同步**   | 门按动作类型保关键信号、原始版留底可恢复；同步让记忆在编辑后仍可信             |

### 什么时候该考虑 ContextSniper

- 你的编码 Agent 上下文成本高、轮次多（read-try-fail-reread 循环）→ 它的 -38.9%~-51.5% token 很实在
- 私有/演进中的代码库，证据散在实现/测试/配置/运行时输出里 → 本地记忆层可查可刷新
- 你想保留现有 Agent 工作流 → 它是插入层，不替换宿主 Agent

### 什么时候可能不适合

- 任务本就极短（5 动作内完成）→ 检索 setup 开销摊不开，反而更费
- 检索召回低（首包没命中决定性文件）→ 会继续搜，token 反增（seaborn 那种）
- 需要跨任务经验复用 → 它不干这个，得配 SWE-Exp/ExpeRepair 那类记忆
- 需要解决率提升而非成本下降 → 当前结果只支持效率主张
