# POC 评估数据集选型方案（低成本版）

> 核心原则：**能用测试结果的就不用人工标，能用Git元数据的就不用人工标，能用LLM-as-judge的就不用人工标。** 人工标注从9人天压缩到2人天。

---

## 一、降本思路：三种自动Ground Truth

| 自动Ground Truth | 来源 | 零标注成本 | 评估什么 |
|-----------------|------|-----------|---------|
| **测试通过/失败** | CI/CD | 0 | 端到端效果（⑦）、冲突解决后代码是否仍正确（③） |
| **Git元数据** | commit message前缀、时间戳、文件路径、author | 0 | 类型先验标签（②）、时间锚定正确性（①）、冲突对自动构造（③） |
| **LLM-as-judge** | 3个LLM交叉评判，Fleiss' κ验证一致性 | 0（API成本） | 提取质量（①）、合成质量（④）、检索相关性（⑤） |

**只有两种东西必须人工标**：
1. **领域术语初始表**——领域专家整理，但可以只整理20个核心术语（1小时）
2. **编码任务设计**——设计10个能体现记忆价值的任务（1天）

**总计：~2人天**（原来9人天）

## 二、重新设计：每个能力的低成本评估方案

### 2.1 事件提取质量（①）→ LLM-as-judge，零人工

**原方案**：人工标注50条commit的三视角条目（2人天）

**低成本方案**：
```
Step 1: 从仓库取100条commit（自动，0成本）
Step 2: POC跑三视角提取（自动）
Step 3: 3个LLM分别评判每条提取结果:
        - 给LLM看: commit diff + 系统提取的Φ/Ψ/Ω条目
        - 问LLM: 提取的事实准确吗？关系正确吗？领域语义合理吗？
        - 3个LLM投票（多数同意为准）
Step 4: 只对3个LLM分歧的条目（预计~10%）人工抽检
```

**成本**：0人天标注 + LLM API成本（100条×3次≈$5）

**可靠性保障**：StructMem论文已验证LLM-as-judge的Fleiss' κ=0.8341（近乎完美一致），方法可靠。

### 2.2 准入控制（②）→ 检索反推 + Git前缀，零人工

**原方案**：人工标"该不该存"（包含在2.1的标注中）

**低成本方案**：用**检索有效性反推准入质量**——存进去了的东西，后面该被检索到时检索到了没？

```
Step 1: 用Git commit前缀作为弱标签（自动）:
        feat: → 类型先验T=0.85(持久知识) → 应准入
        fix:  → T=0.85(Bug修复模式) → 应准入
        refactor: → T=0.85(架构决策) → 应准入
        chore: → T=0.50(半持久) → 边界
        wip:  → T=0.10(临时) → 应拒绝

Step 2: 跑POC准入评分，对比Git前缀弱标签:
        - feat/fix/refactor被准入 → 正确
        - wip被拒绝 → 正确
        - chore的准入/拒绝 → 不计入(边界模糊)

Step 3: 端到端反推: 
        用SWE-bench任务，看任务需要的知识是否在记忆库中:
        - 任务修了Bug X → 记忆库中有相关Bug修复模式 → 准入有效
        - 任务修了Bug X → 记忆库中没有 → 可能准入漏了
```

**成本**：0人天

### 2.3 冲突解决（③）→ Git历史自动构造，零人工

**原方案**：人工构造30个冲突对（1人天）

**低成本方案**：从Git历史中**自动发现冲突**：

```
Step 1: 自动扫描Git历史，找"同一函数/文件被多次修改"的commit对
        - git log --follow <file> → 该文件的所有修改历史
        - 同一函数签名在不同commit中值不同 → 自动冲突对

Step 2: 自动构造冲突场景:
        场景A: commit_old 修改函数F为值X → commit_new 修改函数F为值Y
               期望: commit_new 赢(代码证据+时间更新)
        
        场景B: 找文档目录(docs/)和代码目录(src/)对同一概念的描述
               用LLM自动检测文档vs代码的描述是否矛盾
               矛盾的 → 自动冲突对
               期望: 代码证据赢

Step 3: POC跑冲突解决 → 对比期望(新commit赢/代码赢)
```

**成本**：0人天（脚本自动扫描+LLM自动检测矛盾）

**可靠性保障**：代码场景的冲突解决比对话场景更容易验证——代码能编译能跑就是对的。

### 2.4 跨事件合成（④）→ SWE-bench issue作为查询，零人工

**原方案**：人工设计30个查询+期望结果（2人天）

**低成本方案**：用**SWE-bench的issue描述作为自然查询**：

```
Step 1: SWE-bench的issue描述天然就是"跨commit查询":
        Issue: "核保模块在高龄投保人场景下抛出NullPointerException"
        → 这个issue需要:
          a) 找到高龄投保人规则的commit(原子条目)
          b) 理解这条规则的演进历史(合成记忆)
          c) 找到类似Bug的修复模式(合成记忆)

Step 2: 用测试通过/失败作为Ground Truth:
        - 如果POC注入的记忆帮opencode修对了issue → 合成有效
        - 如果没修对 → 可能合成缺失或不准确
        - 不需要人工标注"期望的合成记忆是什么"

Step 3: LLM-as-judge评估合成质量:
        - 给LLM看: 合成记忆 + 相关commit历史
        - 问LLM: 这条合成记忆是否准确反映了commit间的因果关系?
        - 3个LLM投票
```

**成本**：0人天（SWE-bench自带issue和测试）

### 2.5 双路径检索（⑤）→ RepoBench + 自动延迟测量，零人工

**原方案**：人工设计30个查询分类（包含在跨事件查询集中）

**低成本方案**：

```
Step 1: 直接用RepoBench的查询集(公开数据集,自带Ground Truth)
        - RepoBench本身就是"给定代码上下文,找相关代码片段"
        - 它的Recall@K就是现成的评估指标

Step 2: 自动测量快/慢路径切换:
        - 对每个查询记录: 走了快还是慢? 延迟多少?
        - 用查询的"答案在几条记忆中"自动判断该走哪条路:
          答案在1-2条 → 应走快路径(直接命中)
          答案需要跨3+条 → 应走慢路径(聚类扩展)

Step 3: 延迟自动测量(不需要人工):
        - 快路径p50、慢路径p95
        - 与无记忆基线对比
```

**成本**：0人天

### 2.6 领域知识自进化（⑥）→ 20个核心术语 + 文档自动提取，1小时

**原方案**：领域专家整理50-100个术语（1人天）

**低成本方案**：

```
Step 1: 领域专家只整理20个核心术语(1小时):
        "保单批改""核保规则""赔付系数""免赔额""如实告知"...
        不求全，只求准——20个最核心的够验证机制

Step 2: 用LLM从现有项目文档自动提取更多术语(自动):
        - 扫描 docs/ 目录的markdown
        - LLM提取领域术语 → 补充到初始术语表
        - 不需要人工逐个整理

Step 3: 跑3个Sprint的commit历史 → 看POC自进化产出:
        - 新增术语: LLM-as-judge判断是否合理
        - 更新定义: LLM-as-judge判断是否准确
        - 对比"有注入"vs"无注入"的Ω条目质量
```

**成本**：1小时（20个术语）+ 0标注（LLM自动补充+评判）

### 2.7 端到端编码效果（⑦）→ SWE-bench测试通过率，零人工

**原方案**：人工设计20个编码任务+测试用例（3人天）

**低成本方案**：直接用**SWE-bench-lite的300个任务**，每个都自带测试：

```
Step 1: 选SWE-bench-lite中与目标仓库相关的30个任务(自动筛选)

Step 2: 每个任务跑两遍:
        A: 无记忆(opencode原始) → 测试通过/失败(自动)
        B: 有记忆(POC注入) → 测试通过/失败(自动)

Step 3: 对比:
        - 通过率: B > A 多少?
        - 步数: B < A 多少?
        - 不需要人工评判——测试通过就是通过
```

**成本**：0人天（SWE-bench自带测试Ground Truth）

## 四、低成本评估的可靠性保障

### 4.1 LLM-as-judge够可靠吗？

StructMem论文已验证：3个不同LLM(GPT/Qwen/DeepSeek)交叉评判，Fleiss' κ=0.8341（近乎完美一致）。我们沿用同样的方法：

- 3个LLM投票，多数为准
- 只对3个LLM分歧的条目(~10%)人工抽检
- 相当于100条中只需人工看10条 → 1小时内完成

### 4.2 Git前缀弱标签够准确吗？

Git commit前缀(`feat:`/`fix:`/`refactor:`/`chore:`/`wip:`)是Conventional Commits规范，大多数规范项目都遵循。它天然就是类型先验T的标签：

- `feat:` → 新功能 → 持久知识 → 应准入
- `fix:` → Bug修复 → Bug修复模式 → 应准入  
- `refactor:` → 重构 → 架构决策 → 应准入
- `chore:` → 杂项 → 半持久 → 边界(不计入评估)
- `wip:` → 进行中 → 临时 → 应拒绝

**不计入边界的`chore:`**：避免了模糊地带影响评估精度。

### 4.3 SWE-bench测试通过率够公平吗？

SWE-bench的测试是**确定性的**——测试通过就是通过，不通过就是不通过。没有人工评判的主观性。

唯一风险：SWE-bench的任务可能与你的垂域不完全匹配。缓解方案：
- 从SWE-bench中筛选与保险/金融领域相关的任务（自动关键词匹配）
- 补充5个内部仓库的真实issue（有现成测试的）

### 4.4 自动发现冲突对够全面吗？

可能遗漏一些"文档vs代码"的隐性冲突。但POC阶段不需要100%覆盖——能自动发现**同一函数多次修改**和**文档vs代码描述矛盾**两类冲突就够验证机制了。覆盖率不够可以用LLM-as-judge补：让LLM通读文档和代码摘要，自动标注潜在矛盾。

## 五、最终推荐方案

### 5.1 数据集选型

```
公开数据集(零标注):
  ├─ SWE-bench-lite (30个相关任务) → ⑦端到端 + ④合成质量
  ├─ RepoBench → ⑤检索效果
  └─ CommitChronicles (100条) → ①提取质量

自动构造(零标注):
  ├─ Git历史扫描 → ②准入标签(commit前缀) + ③冲突对(同函数多次修改)
  └─ LLM矛盾检测 → ③文档vs代码冲突对

LLM-as-judge(零人工):
  ├─ 提取质量评判(3LLM投票)
  ├─ 合成质量评判(3LLM投票)
  └─ 术语自进化评判(3LLM投票)

人工标注(2人天):
  ├─ 20个核心领域术语(1小时)
  ├─ 10个跨session编码验证场景(1天)
  └─ LLM分歧条目抽检(~1小时)
```

### 5.2 评估流程

```
第1周: 自动评估
  ├─ 跑CommitChronicles 100条 → LLM-as-judge评提取质量(①)
  ├─ 跑Git前缀标签 → 评准入控制(②)
  ├─ 跑Git历史冲突对 → 评冲突解决(③)
  └─ 跑RepoBench → 评检索效果(⑤)

第2周: 端到端验证  
  ├─ 跑SWE-bench-lite 30个任务(A/B对比) → 评端到端(⑦)+合成(④)
  ├─ 注入20个领域术语 → 跑3个Sprint → 评自进化(⑥)
  └─ LLM分歧抽检 → 人工校验
```

### 5.3 成功标准（不变）

- [ ] 提取精确率 ≥ 85%（LLM-as-judge评判）
- [ ] 冲突解决正确率 ≥ 90%（Git历史自动验证）
- [ ] SWE-bench任务通过率提升 ≥ 15%（测试自动验证）
- [ ] 检索延迟 p50 ≤ 5ms（自动测量）
- [ ] 领域术语识别率 ≥ 85%（20个核心术语验证）

## 六、什么情况下值得投入更多标注成本

如果POC验证通过、决定进入生产级开发，以下场景值得增加标注：

| 场景 | 追加标注 | 成本 | 价值 |
|------|---------|------|------|
| 权重学习数据不足 | 200条commit标注"该不该存" | 4人天 | A-MAC权重更准 |
| 冲突解决需要更多覆盖 | 100个冲突对 | 2人天 | 边缘case覆盖 |
| 垂域任务需要更精细 | 50个内部issue | 5人天 | 业务场景贴合度 |

**但这些都是POC验证通过之后的事——POC阶段用2人天+自动Ground Truth足够判断方案是否可行。**
