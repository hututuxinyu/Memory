## 一、CodeDoc 要解决什么问题？

### 先说大背景

开发者大部分时间不是在写新代码，而是在**理解已有代码**（功能扩展、修 bug、代码审查、维护）。高质量代码文档（函数/类的自然语言描述、docstring）因此至关重要——但手工维护又累又容易过期。于是人们想用 LLM 自动生成文档。

### 现有方法的三类路子 + 四个毛病

| 路子                | 代表                            | 优势                 | 短板                                   |
| ------------------- | ------------------------------- | -------------------- | -------------------------------------- |
| **启发式**          | 模板/规则/相似片段检索          | 可解释、可控         | 难泛化到大仓库，跨文件/跨函数依赖抓不住 |
| **神经模型**        | CodeNN / CodeBERT / PLBART      | 语义建模强           | 多停在函数级摘要，没覆盖全仓库         |
| **LLM 仓库级**      | RepoAgent / RepoSummary         | 纳入目录结构和依赖   | 质量靠 prompt 隐式定义，无显式准则     |

论文把它们的通病归成四条：

| 毛病                          | 通俗解释                                                                 |
| ----------------------------- | ------------------------------------------------------------------------ |
| **缺显式可验证准则**          | "什么是好文档"说不清，工具间/场景间不一致                                 |
| **token 成本高**              | 靠深度递归分析、冗余依赖输入，难以扩展到大仓库                            |
| **长上下文稀释关键信息**      | 上下文过长时，关键信息被无关细节淹没，生成不稳                            |
| **评测靠主观人工**             | 难复现、难横向比较                                                        |

### CodeDoc 的思路

把代码文档生成重定义为**"标准引导的软件工程任务"**——文档的内容/结构/范围由从权威文档标准派生出的**显式、可复用质量准则**约束。一句话：**先用标准定清楚"好文档该满足什么"，再让生成和评测都对着同一套准则干**。

形式化：仓库 $\mathcal{C}=(\mathcal{E},\mathcal{R})$，$\mathcal{E}$ 是代码实体（函数/类），$\mathcal{R}$ 是结构关系。每个实体生成一份文档 $d_e$；质量由准则集 $\mathcal{Q}=\{q_1,\dots,q_n\}$ 治理，每个准则带 1–5 评分函数 $s_i$。目标是均值最大化。注意这只是**概念框架**（说明目标），实际靠"prompt + 按准则反馈精修"逼近，不是直接优化。

## 二、怎么把"标准"变成可执行的准则？（Phase a：离线准则抽取）

这是 CodeDoc 和所有前作最不一样的地方。Phase a **只跑一次**，与任何具体仓库无关，把权威标准变成机器可用的准则集 $\mathcal{Q}$。

### 两个互补来源

| 标准                       | 性质           | 覆盖维度                                                                       |
| -------------------------- | -------------- | ------------------------------------------------------------------------------ |
| **ISO/IEC/IEEE 文档标准**  | 正式工程准则   | 正确性、完备性、一致性、模块组织、可维护性、可访问性、国际化、安全、更新纪律 |
| **GitHub 文档风格指南**    | 实践导向       | 开发者可读性、任务导向组织、可导航性、流程清晰、贡献者易用                     |

ISO 管"工程级完整"，GitHub 管"开发者体验"，互补。

### 两步抽取流程

```
权威标准文档
   │ (i) GPT-5-mini 候选抽取 → 产出 (category, dimension, description, scoring guideline) 过完备集
   ▼
(ii) 人工审查 + 归一化 → 去重、规范措辞、映射到可独立打分的维度
   ▼
固定 schema rubric：每个维度 = 短名(法官变量) + 一句定义(prompt) + 1–5 评分锚点(校准法官)
```

最终两套 rubric：

| Rubric   | 类别数 | 维度数 |
| -------- | ------ | ------ |
| **ISO**  | 7      | 14     |
| **GitHub**| 5      | 12     |

### 为什么这套准则能"一鱼两吃"

$\mathcal{Q}$ 在 Phase b 流入**两个点**：
1. 作为每个 prompt 的**第一块**（让 LLM 对着 rubric 生成）
2. 作为文档法官 + 外部评测者的**评分 rubric**

**同一份显式规范同时管生成和评测**——这正是"standards-guided"的字面含义，也是它区别于"prompt 隐式定义质量"的前作的关键。

## 三、怎么生成文档？（Phase b：在线生成）

Phase b 是每个仓库跑一次的运行时流水线，分两阶段。

### Stage 1：源码分析——建依赖感知的结构表示

目标：建精炼表示 $\mathcal{C}'=(\mathcal{E},\mathcal{R}')$，让 Stage 2 只取依赖相关上下文，不必把整个仓库塞给 LLM。

| 分析                         | 工具    | 产出                                                                 |
| ---------------------------- | ------- | -------------------------------------------------------------------- |
| **调用图分析**               | Pyan3   | 解析 import + 调用点 → 仓库级有向调用图（DOT 格式），caller-callee 边构成 $\mathcal{R}'$ 骨架 |
| **AST 解析**                 | Python AST | 函数签名、参数表、类属性、主要控制流；精确行范围定位，给每个节点附上源码 |

两路互补：调用图抓**全局依赖结构**（不带源码），AST 抓**局部结构线索 + 源码定位**（补全实现细节）。

### Stage 2：标准引导生成——prompt-and-refine 闭环

对每个目标实体，prompt 引擎**只取直接 caller 和 callee**（不暴露整个仓库），按固定顺序拼 4 块 prompt：

| 块   | 内容                                       |
| ---- | ------------------------------------------ |
| (i)  | 从 $\mathcal{Q}$ 来的文档准则定义           |
| (ii) | 目标实体源码 + 仓库路径                    |
| (iii)| 依赖相关实体源码，带 caller/callee 注解（uses / used_by 段）|
| (iv) | 生成指令（输出格式）                       |

LLM 产出文档（按源码路径组织、可追溯），然后**同一阶段内的 LLM 文档法官**用**同一套 $\mathcal{Q}$** 逐维打分 + 给文本反馈。反馈拼回原 prompt，做**一次**重生成（全程只一轮精修）。闭环完成，**无需重复对整个仓库做长上下文分析**。

> 全流程生成 + 评测都用 GPT-5-mini、默认温度。

## 四、走查例子（Fig 3 & 4）

以 `app.py` + `utils.py` 两文件仓库为例，目标实体 `UserService.__init__`：

1. **Pyan3 输出 DOT**：声明 `app__main`、`app__UserService__init`、`utils__validate_input` 等节点 + 边 `main → __init__`、`__init__ → validate_input`；
2. **AST 解析**：给每个节点附行范围（如 `UserService` 在 app.py 第 2–9 行、`__init__` 第 3–5 行），从而能精确切出源码；
3. **Stage 2 检索依赖**：目标 `__init__` 的 caller=`main()`、callee=`validate_input()`，分别填进 `used_by` / `uses` 段，并用 AST 行范围把它们的源码注入；
4. **拼 4 块 prompt**（准则 + 目标源码+路径 + 依赖源码 + 指令）→ LLM 生成 → 法官按 $\mathcal{Q}$ 打分反馈 → 单轮精修。

文档既锚定本实体实现，又感知其在依赖网络中的角色。

## 五、实验结果

**设置**：10 个开源 Python 仓库（AI + 软件基建域），按 `#Class+#Function` 分小(≤200)/中(200–400)/大(>400)，剔除非源码目录。评测用 ISO + GitHub 两套 rubric。法官每维 1–5 分，两种打分策略：单轮 S（所有维一对话）/ 多轮 M（每维独立交互）。分析单位=仓库(n=10)，报均值差、Cliff's δ、Wilcoxon p。

### RQ1：这套评测可信吗？

**(a) 准则敏感度（受控掩码）**：用 PyTorch 2.8 官方文档 >20KB 文件作高质量参照，随机掩 20/40/60%。结果：**两套 rubric 分数随掩码比例单调下降**。ISO 在重掩码下掉得更快（敏感于结构缺失），GitHub 下降更缓（重可读性）→ 准则确实在抓质量，不是乱打分。

**(b) 人机对齐 + 跨法官族稳健**：3 仓库(Flask/NumPy/PyTorch)×15 函数 = 45 对（CodeDoc + RepoAgent），3 名 2 年+ Python 研究生盲评打分；再用 Claude-3.5-Sonnet 同 rubric 重评。

| 方法       | 人工 | GPT-5-mini | Claude-3.5-Sonnet |
| ---------- | ---- | ---------- | ----------------- |
| RepoAgent  | 3.09 | 3.24       | 3.11              |
| **CodeDoc**| **3.61** | **3.79**   | **3.63**          |
| Δ          | +0.52| +0.55      | +0.52             |

- 人工一致偏好 CodeDoc（+0.52；Fleiss' κ=0.51 中等一致）
- 人工 vs GPT-5-mini 法官 **Spearman ρ=0.72**（p<0.001）；人工比 LLM 法官低 0.1–0.2（已知 LLM 法官轻微膨胀）
- 换 Claude-3.5-Sonnet 后相对排名完全保持，两法官维度级 ρ=0.85，方法分差几乎一致（0.55 vs 0.52）→ 缓解同族偏差

### RQ2：CodeDoc 质量更高吗？

基线：**RepoAgent**（最可比的仓库级文档工具）+ **Long-Context**（把目标实体所在整文件喂同一 GPT-5-mini、匹配 token 预算，无准则无依赖选择）。

| 方法          | ISO-S | ISO-M | GitHub-S | GitHub-M |
| ------------- | ----- | ----- | -------- | -------- |
| Long-Context  | 2.87  | 2.93  | 3.01     | 3.08     |
| RepoAgent     | 3.18  | 3.24  | 3.29     | 3.35     |
| **CodeDoc**   | **3.72** | **3.79** | **3.68** | **3.74** |

- 每格最高；比 RepoAgent **+0.39~+0.55**（相对提升 11.6%–17.0%），比 Long-Context **+0.67~+0.86**（相对提升 21.4%–29.6%）
- 全部统计显著（Wilcoxon p<0.05，Cliff's δ>0.6）
- **分类别全胜**：ISO 增益最大在 Content Quality / Information Structure / Format & Presentation；GitHub 在 Content Model / Reference Content

### RQ3：成本、组件、机制可靠性

**(a) 成本-质量权衡（Fig 8）**：x 轴每文档实体 token（对数轴，方法间差约一个数量级），y 轴文档分。**CodeDoc 在 ISO/GitHub 双双落在左上**——比 Long-Context 高分且 token 低约一个数量级，比 RepoAgent 也偏左上。优势来自两侧同时：依赖感知检索**减冗余上下文**（x），标准引导 prompt **提质量**（y）。

**(b) 组件消融（Table III，ISO 单轮，10 仓库均值）**：

| 变体                         | 均分  | 相对 Full |
| ---------------------------- | ----- | --------- |
| Full（双组件）               | 3.73  | —         |
| No Dependency（去依赖检索）  | 3.45  | -0.28     |
| No Prompt（去结构化准则 prompt）| 3.33  | -0.40     |
| Baseline（双去）             | 3.00  | -0.73     |

顺序 Full > No Dep. > No Prompt > Baseline 在**每个仓库**成立。**标准引导 prompt 贡献更大**（-0.40 vs -0.28），但两者互补、缺一不可。

**(c) 静态依赖恢复审计（Table IV）**：Pyan3 在 Flask/NumPy/PyTorch 各抽 50 函数，2 作者独立标注 ground-truth caller/callee。

| 仓库    | Precision | Recall | F1    | 动态边占比 |
| ------- | --------- | ------ | ----- | ---------- |
| Flask   | 91.2%     | 76.4%  | 83.1% | 18.3%      |
| NumPy   | 88.7%     | 71.8%  | 79.4% | 24.1%      |
| PyTorch | 86.3%     | 67.2%  | 75.6% | 31.5%      |
| 均值    | 88.7%     | 71.8%  | 79.4% | 24.6%      |

- **精度高**（86–91%）：Pyan3 很少凭空造依赖边
- **召回中等**（67–76%）：静态分析在动态特性重的代码上吃力；PyTorch 召回最低 + 动态边占比最高(31.5%)
- **下游影响**：依赖完整恢复的函数 ISO 分 3.82，有漏边的 3.51（Δ=0.31，p=0.023）→ 依赖完整性与质量正相关，**静态分析覆盖是未来直接杠杆点**

## 六、为什么"同套准则既管生成又管评测"不构成循环论证？

这是本文最容易被质疑的点（Construct validity 里 rubric circularity）。论文的辩护有三层：

1. **敏感度测试用独立数据**：RQ1.a 用的是**官方 PyTorch 文档**，不是 CodeDoc 产物——rubric 在方法之外被独立验证过；
2. **基线同 rubric**：所有基线都在同一 rubric 下评分，任何"准则对齐膨胀"对各方**等价生效**，不影响相对比较；
3. **跨法官族稳健**：换 Claude-3.5-Sonnet 后排名保持，说明结论不绑死在某一法官上。

逻辑是：循环论证的风险在于"自产自评"，而本文用**外部高质量参照物验证 rubric**、用**同 rubric 平等评所有方法**、用**跨模型复核**——把"既是裁判又是规则"的偏差压到可接受范围。

## 七、局限性（论文自陈）

| 维度         | 局限                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------- |
| **构造效度** | 准则抽取用 GPT-5-mini + 2 作者人工归一，独立标注者一致性仍是未来工作                              |
| **内部效度** | 样本小(n=10)限统计功效；生成+精修+评测同用 GPT-5-mini 有同族偏差风险（跨族对比部分缓解）           |
| **外部效度** | 仅 10 个开源 Python 仓库；Pyan3 抓不住动态 Python 构造(getattr/参数化装饰器/元类/monkey-patch)，漏边降分 0.31；未必能推到动态特性密集或其它语言 |
| **基线不全** | Long-Context 只隔离了"多给上下文"，还缺 retrieval-only 等对照                                       |
| **精修一轮** | 全实验只做一次精修迭代，多轮的边际收益未探                                                         |

## 八、总结：CodeDoc 值得关注什么

### 一句话概括

**把"好文档该满足什么"从模糊 prompt 显式化成从标准派生的准则集，让生成 prompt 和评测 rubric 共用同一份规范**——既提了质量，又靠依赖感知检索把 token 砍了一个数量级。

### 三个最值得借鉴的设计

| 设计                          | 为什么好                                                                                       |
| ----------------------------- | ---------------------------------------------------------------------------------------------- |
| **标准派生准则 $\mathcal{Q}$** | 让"质量"首次变成显式、可复用、可对齐的规范；一鱼两吃地约束生成与评测，告别隐式 prompt           |
| **依赖感知检索（Pyan3+AST）**  | 只取直接 caller/callee，不喂整个仓库——省 token 约 1 个数量级，又保住仓库级连贯性               |
| **同 rubric 闭环精修**         | 法官按维度给文本反馈、单轮重生成，无需重做长上下文分析；评测与生成同源但用独立数据规避循环      |

### 什么时候该考虑 CodeDoc

- 仓库级代码文档生成，且要"按工程标准可度量"而非只要通顺 → 它的 ISO/GitHub rubric 直接可用
- token 预算敏感 → 比 Long-Context 省约一个数量级，比 RepoAgent 也更省
- 想要可复现、可对齐标准的评测范式 → 它的 rubric + LLM 法官(ρ=0.72 对齐人) 是现成模板

### 什么时候可能不适合

- 动态特性密集的 Python 仓库（重 getattr/装饰器/元类/monkey-patch）→ Pyan3 召回掉到 67%，漏边降 0.31 分
- 非 Python 语言 → 现只验证 Python，Pyan3 不通用
- 需要多轮深度精修 → 本文只跑一轮，多轮收益未知
- 想要"下游任务效用"而非"标准对齐分数"的评测 → 那更该看 SWD-Bench 那类（用文档能否让 Agent 干活来评）
