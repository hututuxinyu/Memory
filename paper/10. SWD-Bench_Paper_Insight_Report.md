## 一、SWD-Bench 要解决什么问题？

### 先说大背景

软件文档描述源码的功能与逻辑，是仓库理解的关键。手工写又贵又慢，于是 LLM 驱动的**仓库级文档生成**兴起（RepoAgent、DeepWiki、AutoDoc、DocAgent 等）。但怎么评这些文档好不好？现有基准有两个硬伤。

### 现有基准的两个毛病

| 毛病                          | 通俗解释                                                                 |
| ----------------------------- | ------------------------------------------------------------------------ |
| **缺仓库级分析**              | 现有基准把文档拆成函数/方法级摘要逐个评，忽视跨模块的语义关联；而真实开发者读文档是**整体理解**，要看跨多模块的功能 |
| **评测策略不可靠**            | 三类都有问题：人工评**贵**；BLEU/ROUGE 等**要参考文档**且难构造；LLM-as-a-judge 最流行，但用模糊的 5 级 Likert（"not helpful"/"slightly helpful"），准则含糊，且 LLM 缺仓库实现细节知识，判不准功能描述对不对 |

更深层的问题：这些策略评的是"文档内容质量"，而不是"**文档的实用效用**"。

### SWD-Bench 的思路

借鉴**文档驱动开发（documentation-driven development）**：好文档应该让开发者更有效地理解仓库并实现功能。于是——**不直接给文档打分，而是把 LLM 当成仓库开发者，看它能不能照着文档理解并实现功能**。文档质量由 LLM 在三类功能驱动 QA 任务上的表现来间接衡量。

核心一句话：**文档好不好，看它能不能帮"读者"干成事，而不是看它长得像不像好文档**。

## 二、三类功能驱动 QA 任务

通俗讲：拿一个文档 $D$ 给 LLM，再问它一个功能相关的问题 $Q$，它给出答案 $A$；三个任务的 $Q$ 和 $A$ 各不相同，正好对应开发者读文档的三个连续阶段：

| 任务                         | 模拟的开发阶段         | 问题问什么                     | 答案空间                         |
| ---------------------------- | ---------------------- | ------------------------------ | -------------------------------- |
| **Functionality Detection**  | 查文档：这功能实现没？ | 某功能是否存在于当前仓库       | 二分类 {True, False}             |
| **Functionality Localization** | 定位：功能在哪？      | 实现该功能的文件是哪些         | 一组文件路径（从仓库所有文件里挑）|
| **Functionality Completion** | 补全：细节怎么填？     | cloze 风格，把功能描述里技术细节挖空 | 细节序列（如 API 参数）          |

三类任务串起"查存在 → 定位置 → 补细节"的开发闭环，覆盖文档的**完备性、导航性、详尽性**三个维度。

## 三、怎么构造基准？（三阶段流水线）

SWD-Bench 共 **4,170 条**，构造分三阶段：

### 阶段 1：高质量数据爬取与过滤

```
12 个 SWE-Bench 仓库（每个取一个稳定快照）
   → GitHub REST API 爬取所有 PR（初始 177.4k）
   → 多维过滤 → 4,170 条高质量 PR
```

过滤规则分两组：

| 基础合规过滤                     | 功能相关性过滤                                   |
| -------------------------------- | ------------------------------------------------ |
| 已合并、有 milestone、描述>50字符、合到 main、有 review、非 bot | 有功能标签（new feature/new API）、改了功能目录下的功能文件（如 .py，排除 /test）、功能持久性（PR 合并时间早于快照、新增非注释代码行在快照版本仍存在，考虑文件改名） |

### 阶段 2：仓库级上下文补全

给每条 PR 补四类上下文，奠定仓库级 QA 基础：

| 上下文来源                 | 抓什么                                                     |
| -------------------------- | ---------------------------------------------------------- |
| **程序依赖分析**           | Tree-Sitter 解析改动的完整定义，分析 caller/callee         |
| **关联 issue 检索**        | 正则抽 PR 标题/描述里的 issue 号（如 "closes"），爬 issue 元数据；Django 用自定义爬虫 |
| **外部网页抽取**           | BeautifulSoup 解析 PR 描述里的外链页面（官方文档/社区讨论）|
| **提交历史追踪**           | 每个 commit 的 message、改动、review 评论                 |

### 阶段 3：功能驱动 QA 构造

- **意图引导的功能描述生成**：用 Claude-Sonnet-4 套模板 + CoT（链式思考），按三意图维度生成描述——**WHAT**（构成/受影响的实体）、**WHY**（目的动机）、**HOW**（实现方式）。WHAT/HOW 来自代码+依赖，WHY 来自 commit+issue。**防答案泄漏**：禁止明说文件路径或版本。
- **可靠 QA 对生成**：每个 QA = 功能描述（问题内容）+ Query（问什么）+ 参考答案（从 PR 元数据/上下文**客观抽取**）。三类任务的参考答案分别来自：PR 合并时间判定、PR 改动文件、功能描述里的技术细节。
- **人工质量校验**：随机抽 100 条，2 名 3 年+ Python 专家标注，**Kappa > 90%**。

数据统计：功能描述均长 771.45 字符；检测任务正例占 50.65%；定位任务均需找 2.01 个文件（1–62）；补全任务均需填 7.48 个细节（3–23）。

## 四、评测指标（全部客观、自动计算）

这是 SWD-Bench 和 CodeDoc 最根本的区别——**没有 LLM 主观打分**，全是对照参考答案的自动匹配指标：

| 任务 | 指标 | 公式/含义 |
|---|---|---|
| **Detection** | **B-ACC**（平衡准确率） | 各类召回均值，比标准准确率更能代表 |
| | **MCC**（Matthews 相关系数） | 抗不平衡二分类的可靠指标 |
| **Localization** | **F1**（宏平均） | 预测文件集 vs 参考集的精确/召回平衡 |
| | **IoU** | 预测/参考文件集的交并比 |
| **Completion** | **EM₁.₀**（严格 Exact Match） | 编辑相似度 ≥1.0 才算对 |
| | **EM₀.₈**（宽松 Exact Match） | 编辑相似度 ≥0.8 算对 |

下游效用指标（RQ3）：SWE-Agent **issue-solving rate** + issue 文件定位率。

## 五、实验结果

**设置**：因成本随机抽 480 条评测；GPT-4.1 + Gemini-2.5-Pro 当"开发者"答题（温度 0.2，重复 3 次取均）；文档检索用 SFR-Embedding-Code-400M_R 切块（512 token、10% 重叠）检索 Top-1024/2048/4096 三档上下文。对比 6 种文档：基线 H-Written（人工）、Chat（无上下文）；仓库级 DeepWiki（模块级）、AutoDoc（文件级）、DocAgent（多 agent）、RepoAgent（DAG 全局上下文）。

### RQ1：各方法在 QA 任务上的表现（Table 2 节选）

为了看出"有没有文档差多少"和"最好的能到什么水平"，下表只列**无文档下限**和**表现最好的 RepoAgent**（GPT-4.1 与 Gemini-2.5-Pro 两个基座各一列，数值为百分制）：

| 任务 | 指标 | 无文档 | RepoAgent·GPT | RepoAgent·Gemini | 说明 |
|---|---|---|---|---|---|
| Detection | B-ACC | 48.68 | 63.75 | 69.53 | 接近随机(50)，检测仍难 |
| | MCC | -3.43 | 27.77 | 37.23 | 最高 MCC 仅 29.35，分类能力弱 |
| Localization | F1 | 30.34 | 70.19 | 71.11 | 相对高 |
| | IoU | 28.49 | 66.28 | 67.52 | 但 64.90 的均值仍有明显定位偏差 |
| Completion | EM₁.₀ | 18.40 | 26.87 | 30.05 | 最弱，严格匹配仅 28.09 |
| | EM₀.₈ | 20.74 | 29.72 | 33.88 | 宽松匹配也才 31 出头 |

> MCC 接近 0 等于瞎猜，正数越大越好；IoU/EM 越高越好。

**Finding 1**：文档有用（No Doc 远低于所有方法，绝对提升 5.39%–37.95%），但**当前自动方法仍很有限**——最好的也只到这水平，离实用有差距。

**Finding 2**：按文档粒度排，**细粒度**（RepoAgent、DocAgent，针对代码片段）> **中粒度**（AutoDoc，文件级）> **粗粒度**（DeepWiki，模块级）。细粒度之所以强，是因为能给出参数用法、代码示例等更具体的信息。其中 RepoAgent 又明显强于 DocAgent（六个指标上相对提升 11%–62%），说明**直接把全局上下文塞进 prompt，比靠子 agent 去检索更稳**；有意思的是，人工写的 H-Written 仍具竞争力——因为开发者写文档时天然就纳入了仓库上下文。

**Finding 3**：文档看得越多越好（Top1024→2048→4096 持续提升）；跨基座模型（Gemini 略优于 GPT）**相对排名稳定**（RepoAgent>DocAgent>AutoDoc>DeepWiki），评测可靠。

### RQ2：评测策略本身有效吗？（案例研究，关键证据）

pylint-dev/pylint/8824 这条功能补全任务，涉及跨文件复杂交互（utils.py 的 `in_type_checking_block` 被 diagrams.py 的 `add_from_depend` 调用等）：

| 评测方式 | Chat 文档 | RepoAgent 文档 | 区分能力 |
|---|---|---|---|
| **LLM-as-judge**（Completeness/Usefulness 5 级）| 满分 5 | 满分 5 | **无法区分**（LLM 缺仓库知识，只看表面流畅）|
| **SWD-Bench QA**（填 4 个 MASK）| 0/4 对 | 4/4 对 | **清晰区分** |

**Finding 4**：基于功能驱动 QA 的评测能准确评估文档**实用指导性**，而 LLM-as-judge 给差文档也打满分——这正是 SWD-Bench 要解决的不可靠问题。

### RQ3：文档质量对 issue 解决的影响

57 个 SWE-Bench Verified 实例，给 SWE-Agent 喂 Top-4096 文档：

| 设置 | issue-solving rate |
|---|---|
| 无文档（baseline）| 43.86% |
| DeepWiki | 47.37%（相对 +8.00%）|
| AutoDoc / DocAgent | 49.12%（相对 +12.00%）|
| RepoAgent（最佳）| 52.63%（相对 **+20.00%**）|

issue 文件定位率提升 6.01%–11.19%。

**Finding 5**：**文档质量越高，issue 解决率越高**——RQ1 的质量排名与 RQ3 的解决率排名完全一致，互相印证评测有效性，也证明高质量文档对文档驱动开发的实用价值。

## 六、关键发现汇总（5 个 Finding）

| Finding | 内容 |
|---|---|
| 1 | 文档有用但当前自动方法仍有限，离实用有差距 |
| 2 | 细粒度+全局上下文方法更强；人工文档仍具竞争力 |
| 3 | 深入读文档→更好理解；跨基座模型排名稳定 |
| 4 | QA 评测能区分文档实用指导性，LLM-as-judge 会给差文档打满分 |
| 5 | 文档质量越高→issue 解决率越高，评测与下游效用一致 |

## 七、与 CodeDoc 的对比（两大评测路线）

SWD-Bench 和 CodeDoc 代表文档评测的两大对立派别：

| 轴 | CodeDoc（标准对齐评分派）| SWD-Bench（下游任务效用派）|
|---|---|---|
| **主指标** | LLM-judge 1–5 分均值 | F1/IoU/EM/B-ACC/MCC 客观匹配 |
| **评分依据** | ISO/GitHub 标准派生的 rubric 维度 | PR 抽取的客观 reference answer |
| **评测方式** | 直接按维度打分 | 间接看 LLM 能否照文档干活 |
| **LLM-judge 态度** | 拥抱（同 rubric 闭环精修）| 反对（案例证明它给差文档打满分）|
| **下游验证** | 无 | SWE-Agent 解决率（+20%）|
| **回答的问题** | 文档符不符合工程标准？ | 文档能不能真帮开发者干活？|
| **人工介入** | 3 人验证法官可信度（ρ=0.72）| 2 人验证数据集质量（Kappa>90%）|
| **仓库级** | 单实体级（函数/类）| 跨文件功能级（PR 驱动）|

两者互补而非互斥：CodeDoc 管"生成时按标准约束"，SWD-Bench 管"生成后按效用验收"。

## 八、局限性（论文自陈 + 推断）

| 维度 | 局限 |
|---|---|
| **评测范围** | 12 个 SWE-Bench Python 仓库，非 Python/非 SWE-bench 域未验证 |
| **样本规模** | 因成本评测只抽 480 条子集（全集 4,170 用于构造）|
| **依赖生成方法** | 评测依赖被评方法本身的检索/切分质量，文档检索用固定 embedding 模型 |
| **功能粒度** | 以 PR 引入的功能为单位，非功能性的文档（架构、约定）不在内 |
| **LLM 当开发者** | 答题用 GPT-4.1/Gemini-2.5-Pro，"开发者"能力上限会影响文档效用的体现 |
| **构造偏 Python** | 功能性文件判定、Tree-Sitter 解析偏 Python 生态 |
| **参考答案客观性** | Detection 答案靠 PR 时间判定（机械可靠）；Localization/Completion 靠 PR 改动/描述抽取，质量依赖 PR 本身的规范性 |

## 九、总结：SWD-Bench 值得关注什么

### 一句话概括

**把文档评测从"给它打分"变成"看它能不能让 LLM 当开发者干成事"**——用 PR 驱动的客观 QA 任务对照参考答案自动判分，绕开 LLM-as-judge 的模糊性与知识缺失。

### 三个最值得借鉴的设计

| 设计 | 为什么好 |
|---|---|
| **功能驱动 QA 而非直接评分** | 评的是实用效用而非表面质量；案例证明能区分 LLM-judge 区分不了的文档 |
| **客观 reference answer** | 从 PR 元数据/代码改动抽取，可自动匹配（F1/IoU/EM），可复现、可横向比较 |
| **下游效用闭环验证** | 文档质量排名与 SWE-Agent 解决率排名一致（+20%），评测有效性有硬证据 |

### 什么时候该用 SWD-Bench

- 想客观、可复现地评仓库级文档的**实用价值**而非流畅度 → 它的 QA + 客观指标直接可用
- 想验证文档对 Agent 干活的真实帮助 → RQ3 的 SWE-Agent 解决率范式可借鉴
- 你的文档方法声称"提升开发者效率" → 用它做验收比 LLM-judge 更有说服力

### 什么时候可能不适合

- 需要按工程标准细粒度对齐（如 ISO 维度）→ 那该配 CodeDoc 那类 rubric 评测
- 非 Python / 非 PR 驱动的功能场景 → 现版本未验证
- 只关心单实体文档质量、不关心跨文件功能 → 它的仓库级优势用不上
